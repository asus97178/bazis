# Постоянный локальный стенд JWT

Основание: прямое поручение «создай стенд», 2026-09-14.
Затрагивается эксплуатационная композиция существующего приложения, Auth/JWT
и проверочные утилиты. Новых архитектурных модулей и публичных API приложения нет.

Создать два экземпляра полного AppModule, отдельные PostgreSQL, HTTPS-прокси,
LLM health stub и контейнер генератора нагрузки. Использовать собственную Docker
сеть, именованный том БД, уникальный compose project, раздельные cpuset и лимиты
CPU/RAM. Публиковать только HTTPS на loopback. Сохранить стенд после проверки.
Все credentials синтетические и случайные; runtime-файлы в игнорируемом
`.cache/jwt-stand`, секретные файлы 0600. Не менять другие контейнеры и Docker VM.

Сборка выполняется квалифицированным macOS Bun через scripts/osnova-bun.
Для Docker требуется отдельный Linux arm64 musl бинарник той же версии 1.4.0
и revision. В рамках поручения создаётся изолированный тестовый Linux target:
перед его запуском проверить runtime fingerprint и HS256/RS256/rotation/revocation.
Это не расширение основного toolchain/bun.json и не принятие Linux для релиза
всего проекта. Рабочий launcher и его macOS-проверки сохраняются.

Контракты stand.py: create (новая установка), status (готовность и ресурсы),
start/stop (сохранение данных), verify (TLS/auth и соответствие ресурсов),
test (100 RPS / 300 s / 16 sessions по умолчанию),
destroy (явное удаление только собственного стенда и тестовых данных).
Создание должно проверять существующее состояние и не перезаписывать ключи/БД.
Неверное состояние или несовпадение владельца блокирует операцию.

Поправки после реального запуска: команда PostgreSQL передаётся одним элементом
argv для sh -ec. У proxy две собственные сети: внутренняя stand для backend и
edge для loopback-публикации HTTPS; Docker Desktop не создал host port mapping
у единственной internal сети. Остальные пять сервисов подключены только к stand.
Статус ready требует также действующей публикации и TLS-доступности с хоста.

До завершения: реальный Linux crypto probe, готовность обоих приложений и БД,
TLS с проверкой доверия/имени, bootstrap/login/refresh и отклонение неверного JWT,
отдельный генератор, чтение фактических CPU/RAM limits, stop/start с сохранением
аккаунта. Проверка нагрузки сохраняет первоначальные пороги p95<=250 ms,
p99<=500 ms, каждое 10 s окно p99<=500 ms, scheduler lag p99<=100 ms,
0 неожиданных ошибок; провал не скрывается успешным статусом готовности стенда.

Docker Desktop остаётся на общей физической машине. Cpuset разделяет компоненты
стенда внутри VM; он не резервирует физические CPU от других macOS/Docker задач.
Для независимой серверной приёмки тот же состав требует выделенного хоста.

Основания реализации: [Bun cross compilation](https://bun.sh/docs/bundler/executables),
[Compose resources](https://docs.docker.com/reference/compose-file/services/#cpuset),
[internal networks](https://docs.docker.com/reference/compose-file/networks/).

## Продолжение 2026-09-19: локализация задержек

Существующая эксплуатационная композиция; архитектурный модуль не создаётся.
Ответственность изменения — измерение и воспроизводимая диагностика стенда.
`client.ts` разделяет накопленную очередь одной сессии и задержку пробуждения,
измеряет задержку таймера, GET/refresh и времена ответа proxy. `proxy.ts` добавляет
безопасные числовые заголовки времени до получения upstream headers; тело ответа
остаётся потоковым. `stand.py test` получает ограниченный `--route`:
proxy (default), app-a, app-b, proxy-status. Последние три — диагностические пути,
не замена полного HTTPS/Auth профиля. Произвольных адресов CLI не принимает.

До изменения — короткий контроль исходных бинарников. Затем сборка только
изменённых утилит тем же квалифицированным Bun, проверки измерителя и реальное
бинарное исполнение в Linux. Бинарник приложения, его ключи, БД, CPU/RAM и исходные
пороги сохраняются для сопоставимости. Полный итоговый профиль — 300 s / 100 RPS /
16 сессий, прежние latency/error/RSS gates. Задержка от запланированного старта
по-прежнему включает очередь: новые метрики её не вычитают.

После измерений исправлять только доказанную причину; не считать новый успешный
прогон доказательством устранения старого сбоя без сравнимого объяснения.

Следующий шаг диагностики: `client.ts` измеряет fetch до headers, чтение тела
и проверку/JSON parse отдельно. `proxy.ts` передаёт wall-clock timestamps входа
в handler и подготовки ответа, а локальный GET `/__stand/diagnostics` без входных
полей возвращает ограниченную историю пауз его 20 ms таймера. `LoopProbe.ts`
хранит максимум 512 интервалов с задержкой >=50 ms и счётчик вытесненных записей;
генератор использует такой же измеритель. Часы нужны только для сопоставления
событий в одной VM, не для latency gates; границы интервала таймера не равны
точным границам остановки процесса. Снимки proxy до/после нагрузки находятся
вне измеренного профиля. В историю не попадают токены и содержимое запросов.

После воспроизведения пауз: `SchedulerProbe.ts` читает Linux schedstat, CPU quota
и PSI раз в >=100 ms и при паузе таймера >=50 ms. Записываются приращения CPU time,
runqueue wait, throttling и общей CPU/memory pressure за явно указанный интервал.
Недоступные или сброшенные счётчики не заменяются нулём. Цена чтения измеряется.
Это дополнительная диагностика тех же процессов; настройки Linux не меняются.

Измеренная wall-time цена синхронного чтения иногда велика; после расследования
оно выключается по умолчанию. Явный диагностический вход proxy — переменная
`OSNV_JWT_STAND_SCHEDULER`: отсутствует/`0` (выключено) или `1` (включено),
другие значения прерывают запуск. Client принимает этот режим из снимка proxy
и записывает `profile.schedulerDiagnostics`. Для прямого app-a/app-b он выключен.
Обычная диагностика фаз и ограниченная история таймеров продолжают работать.

CPU-профиль генератора запрашивается операторским флагом `test --cpu-profile`
(boolean, по умолчанию false; для других команд запрещён). Используется текущий
скомпилированный client, без пересборки и изменения Compose. Временное окружение
одного exec включает sampling 1000 µs; cpuprofile и Markdown сохраняются в evidence.
Задержки оцениваются прежними gates. CPU-профиль и включённые Linux-счётчики
делают запуск диагностическим: его PASS не заменяет `lastFullLoad`. Параметры
полного профиля сверяются по фактическому отчёту генератора. Внутренний Linux
timeout ограничивает жизнь нагрузки даже после потери клиентского соединения.

## Продолжение 2026-09-20: размещение исполняемых файлов

Существующая эксплуатационная композиция, без нового архитектурного модуля.
Контракт `package` упаковывает ровно пять уже квалифицированных бинарников
из `state.binaries` в собственный образ на прежней закреплённой базе. Контекст
сборки содержит только эти файлы и Dockerfile. Секреты и конфигурация не входят
в образ. SHA-256 всех файлов проверяется до копирования, после копирования
и внутри образа; Linux crypto probe выполняется из образа без сети.

Основание — сравнение A/B/A одинаковых байтов client: macOS bind mount даёт
2356/1956 major page faults, native image — 0; наблюдаемые ожидания
`folio_wait_bit_common` исчезают у native client. Все три коротких Auth-профиля
остались FAIL по части прежних gates: перенос одного генератора не доказывает
устранения задержек остальных процессов. После упаковки всех бинарников нужны
проверки реального размещения и полный профиль с прежними порогами.

`package` сохраняет резервные state/compose, проверяет новый Compose и меняет
только image пяти Bun-сервисов и bind mount исполняемых файлов. Контейнеры
пересоздаёт отдельный `start`; ключи, БД, CPU/RAM, health checks и API сохраняются.
Образ закрепляется неизменяемым ID и метками владельца/манифеста. `start`
отклоняет несовпадение SHA/владельца/Compose и перекрывающие бинарники mounts.
`status.ready` требует исполнения пяти сервисов из записанного image ID без
перекрывающих mounts. `verify` дополнительно сверяет образ и локальные артефакты.
`destroy` удаляет только собственные runtime-образы после удаления контейнеров;
общий базовый образ сохраняется. Старый стенд мигрирует через `package`, затем
`start`; новая установка упаковывает бинарники автоматически.

Серверная сводка включает целиком последнюю миллисекунду `finishedAt`:
Date генератора округляет время вниз до миллисекунд, Docker timestamp точнее.
Верхняя граница `--until` равна `finishedAt + 1 ms` и явно записана как
`logUntilExclusive`. Это исправляет потерю записи внутри последней миллисекунды,
не меняя измеренные latency, количество запросов или SLO gates.
