# Локальный стенд JWT Osnova

Постоянный тестовый стенд: **https://localhost:18443**.
Полное приложение работает в двух Linux arm64 контейнерах. Данные PostgreSQL,
ключи и учётная запись сохраняются при остановке. Генератор нагрузки — отдельный
контейнер; во время обычной работы он ждёт команду и не создаёт нагрузку.

Проверяемая готовность: `/__stand/status` на HTTPS-прокси и `/health` приложения.
Создание и проверки 2026-09-14 зафиксированы в [отчёте](../../docs/audits/2026-09-14-jwt/STAND.md):
готовность и функциональные проверки PASS, нагрузочный профиль пока FAIL.
В [продолжении 2026-09-19](../../docs/audits/2026-09-19-jwt-performance/REPORT.md)
добавлена диагностика: общий p99 172 ms, но одно окно 515 ms сохраняет **FAIL**
полного профиля. [Следующий этап](../../docs/audits/2026-09-19-jwt-performance/TRACE.md)
локализовал задержки до headers и измерил ожидание CPU; два дополнительных
Auth-профиля также FAIL. [Этап 2026-09-20](../../docs/audits/2026-09-20-jwt-profile/REPORT.md)
добавил изолированный JWT benchmark и CPU-профиль генератора; обычный полный
Auth-контроль прошёл с p99 30 ms. Прежние FAIL сохранены, их причина ещё
не была установлена; этот PASS не является завершением enterprise-приёмки.
Следующее расследование выявило повторные page faults при исполнении бинарников
с macOS bind mount. Теперь исполняемые файлы упаковываются в собственный образ
Linux; происхождение и SHA-256 сохраняются. Это устраняет зависимость подгрузки
кода от файлового обмена с macOS. [Проверка после исправления](../../docs/audits/2026-09-20-jwt-native-image/REPORT.md):
30 000 запросов, 0 ошибок, p99 26 ms, все прежние gates PASS. Прежние FAIL
сохранены; отдельная физическая production-квалификация этим не заменяется.
TLS-сертификат локальный, срок 30 дней с создания. Для запроса из корня репозитория:

```sh
curl --cacert .cache/jwt-stand/certs/server.crt https://localhost:18443/__stand/status
```

## Состав и ресурсы

| Сервис | Назначение | CPU set внутри Docker VM | Лимит CPU | RAM |
| --- | --- | --- | --- | --- |
| app-a | Полный AppModule, первая реплика | 0-1 | 1.5 | 512 MiB |
| app-b | Полный AppModule, вторая реплика | 2-3 | 1.5 | 512 MiB |
| postgres | PostgreSQL 16, TLS verify-full | 4-5 | 1.5 | 768 MiB |
| proxy | HTTPS и выбор здоровой реплики | 6 | 0.8 | 256 MiB |
| load | Проверки и нагрузка | 7-8 | 1.5 | 512 MiB |
| peer | Локальный ответ для LLM health | 9 | 0.25 | 128 MiB |

Cpuset компонентов не пересекаются. Это ограничения внутри общей Docker VM;
физический компьютер и другие контейнеры всё ещё могут влиять на задержки.
Стенд не является отдельной физической машиной и не доказывает SLA продакшена.

Backend использует собственную internal-сеть. У proxy дополнительно есть сеть
edge для публикации **только 127.0.0.1:18443**. У PostgreSQL и приложений нет
опубликованных портов. База образа закреплена:
postgres@sha256:cf78e76683b9ca8c5733cbbdce6c9262b45b6767934dd0a95e671f9a0fc20685.
PostgreSQL использует её напрямую, пять Bun-сервисов — собственный образ с пятью
бинарниками, закреплённый image ID в `state.json` и Compose. Исполняемые файлы
находятся в Linux image layer, без host bind mount. У Bun-сервисов свой entrypoint,
непривилегированный UID, read-only filesystem
и сброшенные capabilities. Внешние SMS/LLM вызовы здесь не проверяются.

## Управление

Команды из корня репозитория, Docker Desktop должен работать:

```sh
/usr/bin/python3 ops/jwt-stand/stand.py status
/usr/bin/python3 ops/jwt-stand/stand.py verify
/usr/bin/python3 ops/jwt-stand/stand.py stop
/usr/bin/python3 ops/jwt-stand/stand.py start
/usr/bin/python3 ops/jwt-stand/stand.py test --seconds 300 --rps 100 --concurrency 16
```

Диагностика отдельных участков, по одному прогону за раз:

```sh
/usr/bin/python3 ops/jwt-stand/stand.py test --route proxy-status --seconds 30
/usr/bin/python3 ops/jwt-stand/stand.py test --route app-a --seconds 30
/usr/bin/python3 ops/jwt-stand/stand.py test --route app-b --seconds 30
/usr/bin/python3 ops/jwt-stand/stand.py test --cpu-profile --seconds 300
```

`--route` принимает только `proxy` (по умолчанию, HTTPS/Auth), `app-a`, `app-b`
(Auth напрямую внутри стенда) или `proxy-status` (HTTPS-ответ самого proxy).
Диагностические пути не заменяют полный профиль. В `lastLoad` сохраняются route,
profile и `fullProfile`: true только для proxy / 300 s / 100 RPS / 16 сессий,
без CPU-профилировщика и дополнительных Linux-счётчиков. Режим Linux-счётчиков
должен быть явно известен и выключен в отчёте генератора.
`lastFullLoad` отдельно сохраняет последний полный профиль: последующий
диагностический PASS не заменяет его результат. Оба поля видны через `status`.
Результат сохраняет image ID и манифест бинарников. `lastFullLoadMatchesImage`
отдельно показывает, относится ли последний полный профиль к текущему образу;
старый PASS после смены образа не подтверждает новую конфигурацию.
Сводка серверных логов включает всю последнюю миллисекунду `finishedAt`:
Docker хранит время точнее генератора. Фактическая граница выборки указана
в `logUntilExclusive`; это не меняет latency и SLO gates.

`status` сверяет принадлежность ресурсов, состояния контейнеров, опубликованный
порт и TLS-доступность с хоста, показывает фактические CPU/RAM. `nativeBinariesReady`
требует записанного image ID для пяти Bun-сервисов и отсутствия mounts,
перекрывающих `/stand/bin`. Контейнер healthy
при недоступном HTTPS не считается готовым стендом.
`verify` также проверяет CPU/RAM по заданной схеме, login/bootstrap, защищённый
доступ, отказ для неверного JWT, refresh, обе реплики и TLS-соединения PostgreSQL.

Новая установка, когда `.cache/jwt-stand` ещё отсутствует:

```sh
/usr/bin/python3 ops/jwt-stand/stand.py create --bun /absolute/path/to/qualified/bun --port 18443
```

Повторный create не перезаписывает существующие ключи и БД. Используйте start.
Миграция ранее созданного стенда с bind-mounted бинарниками или упаковка
обновлённых квалифицированных артефактов:

```sh
/usr/bin/python3 ops/jwt-stand/stand.py package
/usr/bin/python3 ops/jwt-stand/stand.py start
/usr/bin/python3 ops/jwt-stand/stand.py verify
/usr/bin/python3 ops/jwt-stand/stand.py test
```

`package` не компилирует текущие исходники: берёт ровно пять файлов, чьи SHA-256
уже записаны в `state.binaries`. Проверяет байты внутри образа и запускает crypto
probe без сети. Контекст сборки не содержит конфигурации, ключей или credentials.
Сохраняет исходные state/compose в `evidence/package-before-*`, затем обновляет
их; работающие контейнеры меняет отдельный `start`. Между package и start
готовность будет false, если ещё работает прежний образ. Файловые mounts,
которые скрывают бинарники, и несовпадение владельца/хешей блокируют запуск.
Для отката до переключения восстановите оба файла из одной резервной пары.
После переключения откат образа также требует пересоздания Bun-контейнеров;
старый вариант с host bind не проходит новую проверку native readiness.

Удаление стенда **вместе с его тестовыми данными** — отдельная явная команда:

```sh
/usr/bin/python3 ops/jwt-stand/stand.py destroy
```

Операции ограничены уникальным Compose project и проверкой метки владельца
на контейнерах, сетях, томе и собственных runtime-образах. `destroy` удаляет
собственные runtime-образы без force; общий базовый образ сохраняется.
Соседние проекты не включены в состав стенда.

## Файлы и доказательства

Runtime расположен в игнорируемом `.cache/jwt-stand/`:

- `state.json`, `compose.json` — идентичность, состав и текущий статус.
- `bin/` — пять собранных Linux arm64 musl бинарников; источник упаковки,
  SHA-256 проверяется при package/start/verify. Контейнеры выполняют копии из образа.
- `secrets/admin.json` — случайная тестовая учётная запись.
- `secrets/app.json` — конфигурация приложения и случайные ключи JWT.
- `secrets/postgres-password` — пароль только этой тестовой БД.
- `certs/` — локальный сертификат и ключ.
- `evidence/` — сборки, runtime probe, readiness, проверки и нагрузочные JSON.

Каталог runtime имеет режим 0700, секретные файлы — 0600. Секреты не входят
в исходники или отчёт. Логи приложения ограничены ротацией 3 × 10 MiB.
Стенд оставляется запущенным после проверок; stop сохраняет данные, destroy удаляет.

Сборка выполняется macOS Bun 1.4.0 через действующий `scripts/osnova-bun`.
Кросс-компиляция использует официальный Linux arm64 musl runtime той же версии
и revision. [probe.ts](probe.ts) проверяет fingerprint и HS256/RS256, разделение
access/refresh, ротацию, отзыв и malformed JWT в Linux перед запуском приложения.
Основной `toolchain/bun.json` остаётся authority macOS; этот стенд — отдельная
ограниченная проверка Linux, а не расширение релизной квалификации всей платформы.

## Нагрузочный профиль

По умолчанию 300 s / 100 RPS / 16 независимых сессий; примерно 95% GET settings
и 5% последовательных refresh. Login и прогрев соединений не входят в счётчик.
Измеряются задержка от запланированного старта, время запроса, отставание генератора,
10-секундные окна, RSS и cgroup CPU pressure/throttling генератора.

Дополнительные метрики с 2026-09-19:

- `queue` — опоздание сессии к моменту готовности начать следующую операцию;
  `wake` — дальнейшее опоздание после ожидания нужного времени. Их сумма равна
  положительному `lag` каждого запроса. Очередь остаётся внутри latency gate.
- `timerDelay` — задержка отдельного 20 ms таймера в процессе генератора.
  По одному lag нельзя отличить задержку таймера от накопления медленных запросов.
- GET и refresh измеряются отдельно. До 16 самых медленных запросов записываются
  без токенов, тел запросов и персональных данных.
- `upstreamHeaders` и `proxyHeaders` получены из числовых заголовков стенда:
  время fetch до headers от приложения и время обработчика proxy до этой точки.
  Чтение тела и обратная доставка клиенту в эти значения не входят.
- `headers`, `body`, `validate` разделяют время клиентского fetch до headers,
  чтения текста ответа и проверки/JSON parse. Эти длительности измеряются
  монотонными часами; исходная latency по-прежнему измеряется целиком.
- `clientLoop` и `proxyLoopBefore` / `proxyLoopAfter` сохраняют интервалы между
  вызовами 20 ms таймера с опозданием >=50 ms. На процесс удерживается максимум
  512 событий, `eventsSeen` и `dropped` показывают потерю старых записей.
  Снимки proxy получаются через GET `/__stand/diagnostics` без входных полей,
  до/после измеренного профиля. Ошибка последнего снимка отражается отдельно.
  Для выборки прогона используются номера событий после `proxyLoopBefore`.
- В медленных запросах `clientStartedEpochMs`, `clientHeadersEpochMs`,
  `clientBodyEpochMs`, `proxyEnteredEpochMs`, `proxyReadyEpochMs` позволяют
  сопоставить события в одной VM. Wall-clock имеет разрешение в миллисекундах
  и может корректироваться; отрицательная разность не доказывает сетевую задержку.
  `proxyReady` — подготовка Response, не подтверждение его отправки в сеть;
  интервал таймера ограничивает паузу, но не задаёт её точных границ. Wall-clock
  и монотонные часы снимаются последовательно; между отсчётами тоже возможно
  перепланирование, поэтому точность их сопоставления не равна 1 ms.
- `scheduler` у события содержит изменения Linux-счётчиков за явно указанный
  интервал: CPU основного потока/процесса, ожидание runqueue, CPU throttling
  контейнера и общую CPU/memory pressure VM. Чтение выполняется раз в >=100 ms
  и при паузе; `sampleCost` показывает его стоимость, `unavailable` — отсутствующие
  источники. Этот сбор **выключен по умолчанию**: синхронное чтение тоже может
  задержаться и повлиять на измерение. Интервал может включать до 100 ms перед паузой. Разные области
  счётчиков нельзя складывать в разложение времени запроса. Значения основаны на
  [Linux schedstat](https://docs.kernel.org/scheduler/sched-stats.html),
  [cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html) и
  [PSI](https://docs.kernel.org/accounting/psi.html). Диагностика не меняет scheduler.
- Файлы `load-*.resources.json` содержат CPU pressure/throttling, OOM/restarts и
  счётчики PostgreSQL до/после запуска, включая login и прогрев.
  `load-*.application.json` — распределения серверных middleware durationMs
  внутри измеренного клиентского интервала. Ограничение — 50000 строк на реплику;
  полнота этой выборки сверяется по количеству запросов отдельно.

Пороги: p95 <=250 ms, p99 <=500 ms, каждое окно p99 <=500 ms,
scheduler lag p99 <=100 ms, выполнено >=99% запросов, 0 неожиданных ошибок,
рост RSS генератора <=128 MiB. Это прежние инженерные пороги; они не повышаются
из-за неуспешного результата. Параметры CLI: seconds 10..900, rps 1..1000,
concurrency 1..64. Короткая проверка не заменяет профиль 300 s.

Для целевого сбора Linux-счётчиков в локальном `.cache/jwt-stand/compose.json`
задайте `services.proxy.environment.OSNOVA_JWT_STAND_SCHEDULER` строкой `"1"`
и выполните `stand.py start`: Compose пересоздаст proxy с новым окружением.
Генератор автоматически примет режим из proxy и запишет
`profile.schedulerDiagnostics: true`. После диагностики удалите поле или задайте
`"0"` и повторите `start`. Другие значения блокируют запуск proxy. Прямые маршруты
app-a/app-b используют лёгкую диагностику. CPU/RAM и пороги менять не требуется.

`--cpu-profile` допустим только для `test`. Он включает sampling CPU-профиль
**только генератора**, с интервалом 1000 µs, через `BUN_OPTIONS` у отдельного
`exec`. Работающие app/proxy, Compose и бинарники не меняются. Возможность
передачи флага готовому бинарнику описана в
[документации Bun](https://bun.sh/docs/bundler/executables#runtime-arguments-via-bun-options)
и проверена на закреплённом Bun 1.4.0. После завершения сохраняются
`load-*.cpu.cpuprofile` и `load-*.cpu.md`; ссылки на них — в `cpuProfile.files`
JSON-отчёта. Файлы читаются через `exec` из tmpfs, затем временный каталог удаляется.
Неполный или отсутствующий профиль прерывает команду и не публикует успешный результат.
Флаг `profile.cpuProfiler` и признак `lastLoad.diagnostic` записывает оператор;
исходный stdout генератора также сохраняется. Пороги остаются прежними.
Sampling влияет на испытуемый процесс; профиль стека не объясняет сам по себе
причины ожидания CPU или сетевого ответа. Для обычных запусков `BUN_OPTIONS`
у отдельного exec сбрасывается, чтобы исключить наследование флагов профилирования.

Все нагрузки дополнительно ограничены `timeout` внутри контейнера: измеренная
длительность +45 s, затем до 5 s на остановку. Это ограничивает оставшийся процесс,
если клиент Docker потеряет соединение. Проверка правил сохранения результатов
без запуска контейнеров: `/usr/bin/python3 ops/jwt-stand/test_stand.py`.

Этот load проверяет устойчивую работу раздельных контейнеров. Он не управляет
ротацией под нагрузкой: сценарии rolling restart/отзыва и их предыдущие результаты
описаны в [APPLICATION.md](../../docs/audits/2026-09-14-jwt/APPLICATION.md).
Простой HTTPS proxy реагирует на health каждые 2 s; автоматическое переключение
при аварии может дать ошибку запроса в этом промежутке и требует отдельной проверки.
