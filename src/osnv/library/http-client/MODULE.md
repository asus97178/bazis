# HTTP client library

Версия паспорта: 6. Дата сверки: 2026-09-20.
Тип: атомарная библиотека одной функции; собственного DI-модуля нет.
Путь: `src/osnv/library/http-client`. Публичный вход: [index.ts](index.ts).
Статус и область: согласованный режим redirects, исправления HTTP-05/06/08/09 и транспортных контрактов HTTP-E01–E04. Полный перечень полей остаётся в [types.ts](types.ts); фабрика именованных клиентов и interceptors здесь не переописываются.

## 1. Ответственность и структура

Дополнение 2026-09-20: `maxResponseBytes` и `onDownloadProgress` сохраняют ответы
204/205/304 без создания нового Response с телом. В браузере может быть доступен
пустой ReadableStream даже при таком статусе; попытка обернуть его приводила к
ошибке конструктора Response при успешном logout. Публичные параметры не меняются.
Проверки: `test/http-client.bodyless.test.ts`, реальный logout Vue-клиента.

`HttpClient` выполняет HTTP-запросы поверх Fetch, отвечает за URL, redirects, retries, ограничения ответа и представление ошибок. Владеет конфигурацией экземпляра и попыток запроса. ORM, авторизация приложения и DI-регистрации находятся за границей библиотеки. Атомарные подмодули не используются: реализация одной функции.

## 3. Подключение и DI

Вызов: `new HttpClient(defaults).request(config)` либо методы `get/post/...`.
TypeScript-экспорты остаются в `index.ts`; добавлены `HttpErrorCode.BadResponse`, `HttpErrorCode.RedirectNotInspectable` и общий wire-контракт `InspectableRedirectProtocol`. Его read-only поля `header`, `statusHeader`, `version` равны соответственно `x-osnv-redirect`, `x-osnv-redirect-status`, `manual-v1`; пользовательских аргументов у константы нет. DI `imports`, `exports`, providers и lifetime неприменимы. Интеграция [core/http-client](../../core/http-client/index.ts) зависит от библиотеки; обратной зависимости нет.

## 4. Конфигурация и lifecycle

Повторы разрешены только для поддерживаемых идемпотентных методов с воспроизводимым телом. Один deadline охватывает попытки и задержки; сигналы передаются Fetch. `responseType: "stream"` передаёт поток потребителю, который обязан дочитать или отменить его. Producer cleanup запускается при отброшенном ответе, но его незавершающийся Promise не удерживает retry, redirect или отказ по размеру. Библиотека не может завершить произвольный пользовательский код, игнорирующий переданный AbortSignal.

Без согласованного режима (`inspectableRedirects: false`) браузерный Fetch скрывает Location ручного redirect. Запрос без тела с безопасными заголовками может следовать между origin: сам Fetch удаляет `Authorization` при таком переходе. При старте с origin страницы/worker сохраняются его cookies через `credentials: "same-origin"`; чужому origin cookies не отправляются. При старте с внешнего API используются `credentials: "omit"`. Явный `mode: "same-origin"` сохраняется.

Произвольные API-key заголовки, тело и `credentials: "include"` требуют ограничения `mode: "same-origin"` для запросов к origin страницы/worker либо явного `allowCrossOriginCredentials`. Для внешнего API первый запрос работает через CORS, но скрытый redirect с такими данными блокируется без разрешения. Ограниченные correlation-заголовки продолжают запрещать неподконтрольное перенаправление даже при разрешении credentials; политика `all` допускает их отправку. Bun/Node сохраняют пошаговую очистку заголовков.

Браузерный Fetch имеет предел 20 переходов. Без согласования при бюджете 20–100 используется этот более строгий предел. При 0 переход запрещён; при 1–19 обычный ответ принимается, но opaque redirect отклоняется до перехода, поскольку его адрес и дальнейшее число переходов нельзя проверить. Для точного лимита используется согласованный режим из §7. Проверочных запросов с последующей повторной отправкой нет.

## 5. Изменяемые входы и результаты

Потребитель — код приложения. Право обращения к внешнему API и значения секретов задаёт приложение. Библиотека проверяет транспортные ограничения, но не выполняет прикладную авторизацию. Добавлено необязательное поле `inspectableRedirects`.

| Поле | Тип / null | Default | Проверка и действие |
|---|---|---|---|
| `url`, `baseUrl` | `string`, null нет | URL из запроса/настроек | Query добавляется перед `#fragment`; относительный URL поддерживается браузером |
| `params` | `RequestParams`, null у значений | отсутствует | Массивы повторяют ключ; null/undefined пропускаются |
| `paramsSerializer` | функция, null нет | штатный serializer | Готовая строка query вставляется до fragment |
| `redirect` | `follow/manual/error`, null нет | `follow` | Browser manual возвращает opaque response со status 0 |
| `maxRedirects` | safe integer, null нет | 20 | 0–100; Bun/Node и согласованный режим браузера считают каждый переход. Native browser: 0 запрещает redirect, 1–19 отклоняет opaque redirect до перехода, 20–100 использует native cap 20 |
| `inspectableRedirects` | boolean, null нет | false | При true и `follow` согласует видимые redirects с сервером; небулевое значение отклоняется до отправки |
| `allowCrossOriginCredentials` | boolean, null нет | false | Явное разрешение отправки секретов/тела за границу origin; CORS и правила browser Fetch сохраняются |
| `validateStatus` | функция или null | 200–299 | Вызывается один раз; null отключает только проверку статуса |
| `responseType` | перечисление в `types.ts`, null нет | по Content-Type | Невалидный JSON отклоняется и при принятом статусе |

Все поля необязательные и сливаются с настройками клиента; для сетевого вызова нужен разрешимый URL. Ошибка декодирования не удаляет HTTP-контекст:

| Результат | Значение |
|---|---|
| `ERR_BAD_STATUS` | Статус отклонён, включая случай повреждённого JSON |
| `ERR_BAD_RESPONSE` | Статус принят, но JSON повреждён |
| `error.status`, `.response` | Содержат статус, заголовки, config, raw Response; при повреждённом JSON `data` содержит уже прочитанный текст |
| `error.cause` | Исходный `SyntaxError` при повреждённом JSON |
| `ERR_NETWORK` | В том числе блокировка браузерного redirect, CORS, достижение native redirect cap |
| `ERR_REDIRECT_NOT_INSPECTABLE` | Невозможно проверить ручной redirect либо отсутствует/некорректно подтверждение согласованного режима; без автоматического retry |
| `ERR_TOO_MANY_REDIRECTS` | Превышен доступный для точного подсчёта лимит; следующий запрос не отправляется |
| `HttpClientError` без code | Невалидный `maxRedirects` (нецелое значение или вне 0–100), до сетевого вызова |

Ошибки пользовательских progress/transform callbacks не переименовываются в ошибки JSON. Raw-текст ошибки может содержать данные сервера: политика логирования остаётся у приложения.

## 7. Согласованные redirects

Новая опция `inspectableRedirects?: boolean`, источник — defaults/config запроса, default false, null и небулевые значения запрещены до сетевого вызова. При `redirect: "follow"` значение true включает пошаговый протокол с одноимённой опцией нашего HTTP-сервера. При `manual/error` сохраняется выбранный штатный режим; согласование не отправляется.

Каждая попытка и каждый переход отправляет `X-osnv-Redirect: manual-v1` через Fetch с `redirect: "manual"`, `cache: "no-store"`. Успешный ответ обязан подтвердить `X-osnv-Redirect: manual-v1`. Redirect представлен HTTP 200 с заголовками `X-osnv-Redirect-Status: 301|302|303|307|308` и Location; обычный ответ не содержит заголовка статуса. HEAD использует те же заголовки без тела. Метаданные redirect обрабатываются до пользовательского декодирования: клиент проверяет адрес и лимит перед следующим запросом. Нового JSON-envelope нет, секреты и Set-Cookie в тело не копируются.

В этом режиме точный `maxRedirects` 0–100 применяется в браузере тем же кодом, что и в Bun/Node. Для смены origin действуют существующие правила удаления секретов, correlation и запрета переноса тела. CORS и `mode` браузера сохраняются. Нет пробного запроса, повторной отправки для определения redirect, фонового прокси или серверного доступа к произвольным URL.

Отсутствующее подтверждение, некорректные metadata или opaque redirect → `ERR_REDIRECT_NOT_INSPECTABLE`, без автоматического retry. HTTP-ошибка 400–599 без закодированного redirect-статуса сохраняется даже без подтверждения: она не может скрывать согласованный redirect с wire status 200. Это сохраняет, например, HTTP 500 от нативной ошибки открытия файла после pipeline. Превышение доступного для подсчёта лимита → существующий `ERR_TOO_MANY_REDIRECTS`. Режим требует поддержки HTTP-получателей в цепочке; для обычного внешнего API он не включается. В нативном режиме opaque redirect, который клиент не может проверить, также получает отдельный код `ERR_REDIRECT_NOT_INSPECTABLE`.

Пример: `new HttpClient({ inspectableRedirects: true, maxRedirects: 2 })` вместе с `httpModule({ inspectableRedirects: true })` на сервере. Настоящий Chromium проверил лимиты 0/1/2/19/20/100, HEAD, POST 301/302/303/307/308, CORS/секреты, timeout, Worker и неподдерживающий сервер. Строгий серверный `cors.allowedHeaders` должен разрешать `X-osnv-Redirect`; ответы сохраняют существующие CORS origins/credentials. Перенаправления без Location не являются согласованными переходами; браузер может скрыть такой некорректный redirect за opaque response.

## 8. Чтение тела и исходный Response

`RequestConfig.data` по-прежнему принимает `BodyInit`. Для `ReadableStream`
клиент передаёт Fetch `duplex: "half"`, необходимый Node; тело не буферизуется.
Поток остаётся однократным: retries с ним отключены, 307/308 не могут его повторить.
Ограничения потоковой отправки выбранного браузера/Fetch сохраняются.

Обрыв при буферизованном чтении (`text`, JSON, `arrayBuffer`, `blob`, progress)
возвращает `HttpClientError` с `ERR_NETWORK` и исходной ошибкой в `cause`.
Фактическая отмена/timeout сохраняют `ERR_CANCELED`/`ETIMEDOUT`.
Преобразование выполняется только вокруг чтения тела, поэтому исключение
progress/transform callback сохраняется даже при имени `TimeoutError`.
После частичного чтения запрос автоматически не повторяется.

`maxResponseBytes` ограничивает байты, доступные после декодирования Fetch,
включая распаковку. `Content-Length` проверяется заранее только без
`Content-Encoding` либо при `identity`; размер сжатого представления не
сравнивается с размером распакованного. Проверка каждого читаемого chunk
сохраняет защиту от чрезмерного увеличения тела после распаковки.
При CORS отсутствие видимого `Content-Encoding` не доказывает `identity`:
этот заголовок может быть скрыт, хотя `Content-Length` доступен. В таком случае
клиент использует фактический размер потока, не отклоняя маленький gzip заранее.
Ограничитель сохраняет собственную причину отказа: если браузерный
`Response.text/arrayBuffer/blob` заменяет ошибку потока на `TypeError`, результат
клиента всё равно содержит `ERR_RESPONSE_TOO_LARGE`.

`HttpResponse.raw` всегда указывает на исходный Fetch Response, в том числе
при progress, ограничении размера, HTTP-ошибке и повреждённом JSON. URL/type
и другие метаданные не теряются, тело не клонируется и не читается дважды.
`raw.body` может быть уже прочитан или занят reader ограничителя.
При `responseType: "stream"` потребитель читает/отменяет `data`, сохраняя лимит;
ошибки дальнейшего чтения этого потока поступают через его API.
