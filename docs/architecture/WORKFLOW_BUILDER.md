# Бизнес-процессы из коробки: конструктор

Идентификатор: **WORKFLOW-002**. Версия: **1.11**. Дата: **2026-11-02**.
Статус: **утверждено владельцем 2026-11-01** (согласовано агентами bazis и bazis-cms; права — [ACCESS-001](ACCESS.md)).
Основа: [WORKFLOW-001](WORKFLOW.md) (этапы 1–5, bazis 0.124.0–0.128.0),
[TOOLS-001](TOOLS.md), прототип дизайнера
<https://claude.ai/artifact/SZDPQ1N7xU7qLiyZ4siz5n>, обсуждение агентов
bazis и bazis-cms 2026-10-31, рецензия агента bazis-cms (v1.1).

## 1. Цель и правило границы

Разработчик ставит только фреймворк — бизнес-процессы работают целиком: всё,
что есть в прототипе как понятие процесса, исполняется, хранится и доступно по
HTTP. Он добавляет свои роли и доступы, свой UI и свои действия (Tools).
Разработчик ставит bazis-cms — всё работает без дописывания логики процессов.

Правило: **понятие процесса и его исполнение — во фреймворке; предметные
действия и данные — Tools приложения; права, ссылки и данные приложения —
через порты.** Два запрета:

- приложение не хранит документы, версии и экземпляры процессов и не пишет
  свой движок;
- фреймворк не знает о Data Manager, пространствах CMS и языках интерфейса.

Прототип — целевой конструктор. Его модель (шаги списком, ветки «Да/Нет»,
тело цикла) — вид редактора, а не формат исполнения (§3).

### 1.1 Процессы живут без CMS

bazis-cms — один из потребителей, без особых прав в контракте. Любой
разработчик может построить на процессах фреймворка свою CMS или своё
приложение. Отсюда требования:

- **Ничего во фреймворке не названо и не устроено по CMS.** Термины
  контракта общие: раздел (`partition`), ссылка (`x-ref`), расширение
  (`extensions`), Tool. Data Manager, пространства и `cms` встречаются только
  как примеры и в §8.
- **У каждого порта рабочая реализация по умолчанию** (§6): приложение без
  своих портов получает работающие процессы, а не набор заглушек.
- **Действия с данными из коробки.** `ormEntityTools` (§7.4) делает Tools
  «найти / создать / изменить / удалить» из сущностей ORM приложения: блок
  «Каталог» прототипа работает на одном фреймворке.
- **Эталонное приложение без CMS.** В репозитории фреймворка —
  `examples/workflow` (на основе лабораторного приложения «Заказы»): каждый
  блок и запуск прототипа, свои Tools, свои права, тест на `testWorkflow`.
  Каждый этап сначала проходит на нём в CI с PostgreSQL; проверка в CMS —
  вторая, а не единственная.
- **Всё для своего дизайнера:** палитра как данные, `/workflow/validate`,
  `isStructured`, HTTP с JSON:API. Готовых экранов дизайнера во фреймворке нет
  (§11.2).

## 2. Решения обсуждения

Выбор, который сделан, и почему; отвергнутое — тоже.

| Вопрос | Решение | Отвергнуто и почему |
| --- | --- | --- |
| Формат исполнения | Граф (`bazis.workflow/v2` — развитие v1) | Список шагов как формат: теряет произвольные переходы и граничные события, движок пяти выпусков ушёл бы в переделку |
| Вид редактора | Структурное подмножество графа (§3.6); дизайнер приложения рисует его как в прототипе | — |
| Ядро дизайнера | «Безголовое» ядро в `bazis/library/workflow` (§3.8): структура ↔ граф, текстовый синтаксис выражений ↔ JSON-дерево, палитра → описание форм | Синтаксис выражений в каждом дизайнере свой: процесс из одного дизайнера читался бы в другом иначе |
| Выражения | JSON-дерево с закрытым списком функций (§3.3); текст `{amount} * 1.2` — только в дизайнере | Текстовый язык с парсером: дорого, риск инъекций |
| Действия с данными, HTTP, уведомления | Только Tools | Порт `WorkflowDataSource`: второй путь действий, CRUD «наименьший общий знаменатель» |
| HTTP-запрос и секреты | Необязательный модуль стандартных Tools `bazis/core/tools` (§7), закрытый по умолчанию | В ядре движка: фреймворк стал бы продуктом; только в приложении: на одном фреймворке «из коробки» не работает |
| Настройки процесса | Внутри версии документа (§3.5) | Колонками: каждое новое поле — новое хранилище |
| Карточка процесса | Во фреймворке: локализованные названия, папка-путь, владелец-id (§4.1) | В CMS: у приложения на фреймворке нет каталога «как в прототипе» |
| Названия | `LocalizedText` — язык → текст, язык по умолчанию из настроек | Пара `{ru, en}`: зашивает языки CMS |
| Задачи сотрудникам | Остаются (`userTask`, часть Tasks) | Убрать как отсутствующие в прототипе: «ждать решения менеджера» и есть задача |
| Списки HTTP | JSON:API (`bazis/library/jsonapi`) | `limit`/`offset`: второй стиль в одной админке |
| Аудит | События после успешных действий (§4.4); журнал пишет приложение | Свой журнал аудита во фреймворке |
| Актор шага | `context.actor` в Tool (§6.1); «от имени» — настройка процесса; поле `author` в Tools CMS — необязательное переопределение (решение владельца, §11.1) | Только `author` в данных процесса |
| Права на процессы | Общий слой прав фреймворка [ACCESS-001](ACCESS.md): `WorkflowModule` объявляет каталог `workflow.*`, система прав приложения отдаёт гранты, проверку и фильтр делает фреймворк (§6.2) | Роли из claim и карта «роль → действие» в настройке workflow (v1.4): вторая система прав; порт `WorkflowAccess` с условиями в коде приложения (v1.5): императивно и отдельно под процессы |
| Данные приложения в документе | `extensions` по пространствам имён в корне, узлах и переменных (§3.1) | Хранить рядом с документом в CMS: дубль вернётся |

## 3. Документ `bazis.workflow/v2`

Тот же граф v1 (`nodes`, `flows`, `diagram`), плюс то, что ниже. Все 13 видов
узлов v1 остаются с тем же смыслом.

### 3.1 Корень

```ts
interface ProcessDocument {
  schemaVersion: "bazis.workflow/v2";
  variables?: VariableSpec[];          // §3.4, вместо input v1
  settings?: ProcessSettings;          // §3.5
  nodes: Record<string, ProcessNode>;  // title: LocalizedText
  flows: Record<string, ProcessFlow>;  // title?: LocalizedText, condition?: Expr
  diagram?: ProcessDiagram;
  extensions?: Record<string, unknown>; // данные приложения по пространствам имён, например "cms"
}
type LocalizedText = string | Record<string, string>; // строка — язык по умолчанию
```

`extensions` есть и у узлов, и у переменных. Ключ — пространство имён
приложения; значение проверяет порт `WorkflowExtensions` (§6). Пространство
имён без зарегистрированной проверки — ошибка при сохранении черновика и
публикации. Уже опубликованная версия с таким ключом исполняется: движок
`extensions` не читает, поэтому снятый модуль приложения не ломает живые
процессы. Так CMS хранит в
процессе «где показать кнопку запуска» (карточка записи таблицы, список,
массовое действие), правила полей Data Manager и т. п., не держа документы
рядом.

### 3.2 Новые виды узлов

| Вид | Роль | `config` |
| --- | --- | --- |
| `assign` | шаг | `assignments: { var, value: Expr }[]` — переменные процесса |
| `loop` | контейнер | `over?: Expr` (коллекция) \| `while?: Expr` \| `times?: number`; `item`, `index` (имена), `maxIterations` (обязателен, ≤ 10 000), `parallel?: { limit }`, `onItemError: "stop" \| "skip"`, `collect?: { from: Expr, to: var }` |
| `callProcess` | шаг | `process` (ключ), `input` (параметр → `Expr`), `saveTo?`; ждёт конца дочернего экземпляра, результат — его выходные переменные |

Тело цикла — узлы с `parent: "<id цикла>"`: свой подграф с одним входом (шаг без
входящих переходов), со своим `end` и без выходов наружу; переходы через границу
контейнера запрещены. Итерация — свой набор токенов в том же экземпляре; переменные
итерации видны только телу. `saveTo` и `$nodes` в теле принадлежат итерации, если
переменная не объявлена в `variables`. Элемент и номер — всегда `$item` и `$index`
внутреннего цикла; `item` и `index` в `config` дают им ещё и имя `$vars.<имя>`, так
тело видит элемент внешнего цикла. Открытых корней `$<имя>` нет: строка `$что-то` во
входе инструмента должна оставаться литералом.

### 3.3 Выражения

`Expr` — JSON-дерево, проверяется проверкой документа, исполняется без `eval`:

```json
{ "op": "mul", "args": [{ "path": "$vars.amount" }, 1.2] }
{ "op": "concat", "args": ["https://api/orders/", { "path": "$input.orderId" }] }
{ "op": "gt", "args": [{ "path": "$event.record.amount" }, 100000] }
```

- Листья: литерал JSON или `{ "path": "…" }`.
- Функции — закрытый список с типами: арифметика (`add` `sub` `mul` `div`
  `mod` `round`), сравнение (`eq` `ne` `gt` `gte` `lt` `lte` `in` `contains`
  `empty` `notEmpty`), логика (`and` `or` `not` `if` `coalesce`), строки
  (`concat` `lower` `upper` `trim` `length` `format`), даты (`now` `dateAdd`
  `dateDiff` `toDate`), списки (`length` `first` `pluck`).
- Вычисление не падает: что нельзя вычислить (нет значения в арифметике, деление
  на ноль, неверная дата), — `null`, сравнение с `null` ложно. Даты — ISO-строки;
  `dateAdd(дата, "P1D")`, `dateDiff(конец, начало, unit?)`, `format("{0}", a)`.
- Новая функция — новая минорная версия формата. Условия v1 (`all`/`any`/`not`
  и сравнение) переводятся в выражения один в один.
- Пределы: глубина 16, 200 узлов на выражение.

Пути (`$` и имя):

| Путь | Что |
| --- | --- |
| `$input.x`, `$vars.x`, `$nodes.Node.x` | Как в v1 |
| `$item`, `$index` | Элемент и номер внутреннего цикла |
| `$event` | Данные события, запустившего или продолжившего процесс |
| `$trigger` | `{ via, at, actor, eventKey?, cause? }` — как запущен |
| `$run` | `{ id, processKey, version, partition, test }` |
| `$now` | Время по часам движка (`WorkflowClock`) |
| `$secrets.NAME` | Только во входе Tool; подставляет исполнитель (§7.2) |

### 3.4 Переменные

```ts
interface VariableSpec {
  name: string;                         // ^[a-z][A-Za-z0-9_]{0,39}$
  type: "string" | "text" | "number" | "integer" | "boolean" | "date" | "datetime" | "enum" | "object" | "list" | "ref";
  direction: "in" | "local" | "out";
  title?: LocalizedText;
  default?: unknown;
  required?: boolean;                   // для in
  values?: (string | number)[];         // для enum
  ref?: string;                         // для ref: вид ссылки, например "orm.entity:Order" (§6.3)
  personal?: boolean;                   // персональные данные: маскируются в истории при log.maskPersonal
  extensions?: Record<string, unknown>; // правила полей приложения и т. п.
}
```

`in` — вход запуска (форма ручного запуска и тело `start`), `out` — что
процесс возвращает вызвавшему (`callProcess`, ответ API). Поля форм задач —
тот же `VariableSpec` без `direction`: `{ fields: [...] }`. Порт `WorkflowInputValidator` получает
`extensions` поля и проверяет значения по ним: так правила Data Manager живут
в документе без того, чтобы фреймворк их знал. `FormIssue.code` — строка:
правила приложения дают свои коды (`minLength`, `range`).

### 3.5 Настройки процесса (в версии документа)

```ts
interface ProcessSettings {
  runAs?: "starter" | "process";        // от инициатора (по умолчанию) или от системного актора процесса
  runTimeout?: string;                  // ISO-длительность на весь запуск, ожидания входят
  stepTimeout?: string;                 // по умолчанию для шагов с Tool
  maxConcurrent?: number;               // одновременных running-экземпляров процесса
  sameKey?: "allow" | "skip" | "queue"; // новый запуск с тем же businessKey, пока старый идёт
  errorHandler?: string;                // ключ процесса, который запускается при failed/timedOut с $event = сведения об ошибке
  log?: {
    variables?: boolean;                // значения переменных на каждом шаге в истории (по умолчанию false)
    toolPayloads?: boolean;             // вход и выход Tools целиком, в том числе тела HTTP (по умолчанию false)
    maskPersonal?: boolean;             // переменные personal: true — "***" в истории и журналах (по умолчанию true)
  };
}
```

Общие поля `config` шага с Tool: `timeout`, `retry: { maxAttempts, backoff,
growth: "fixed" | "exponential", factor? }` (v1 — `exponential`, множитель 2),
`onError: "fail" | "skip"` (`skip` — шаг пропущен, выход `{ skipped: true,
error }`; граничный `boundaryError` важнее `onError`).

Неизвестная настройка — ошибка `settings_invalid`, а не молчаливо пропущенное
значение. Поэтому в типах она появляется вместе с этапом.

Системный актор процесса — `{ kind: "system", id: "process:<key>" }`. Кто
может так запускать, решает право `workflow.processes.publish` (§6.2).

### 3.6 Структурное подмножество

`isStructured(document)` в `bazis/library/workflow` говорит, рисуется ли граф
как список прототипа: последовательности, развилка `exclusiveGateway` с
одним слиянием, `parallelGateway` со слиянием, контейнер `loop`, граничные
события на шагах. Дизайнер приложения редактирует такие процессы; остальные
(например, из кода) показывает только для чтения. Развилка, все ветви которой идут
в один конец, слияния не требует. Проверка структурности — предупреждение
`not_structured`, не ошибка.

### 3.7 Переход с v1

`upgradeDocument(v1) → v2` — чистая функция: `input` → переменные `in`, `code`
поля формы → `name`, условия → выражения, `title` как есть. Параметры инструмента
не меняются: путь строкой (`"$input.x"`) остаётся рядом с выражением. Опубликованные
версии и черновики v1 переводит через неё перенос при старте (§9), поэтому движок
читает только v2; сохранять можно только v2. Перенос и `upgradeDocument` удаляются в
выпуске после перехода bazis-cms (данных v1 в проде нет).

### 3.8 Ядро дизайнера

Чистые функции `bazis/library/workflow` для любого дизайнера:

- `toStructure(document)` / `fromStructure(structure)` — граф ↔ дерево шагов
  прототипа (последовательность, развилка, параллельный блок, цикл);
- `parseExpression(text)` / `printExpression(expr)` — текстовый синтаксис
  (`{amount} * 1.2`, `concat({a}, "-", {b})`, `now()`) ↔ JSON-дерево §3.3;
  один синтаксис на всех, печать обратима. `{amount}` — `$vars.amount`, остальные
  пути полностью (`{$input.a}`); операторы `+ - * / %`, `== != > >= < <=`,
  `and or not`; сравнения не идут цепочкой; списки и объекты — JSON-литералы;
- `formOf(kind | toolContract)` — описание формы настройки шага по палитре
  (поля, типы, ссылки `x-ref`, локализуемые подписи).

## 4. Каталог (Definitions)

### 4.1 Карточка

`title`, `description` — `LocalizedText`; `folder` — строка-путь
(`Продажи/Заказы`), без сущности «папка»; `owner` — непрозрачный id;
`retentionDays` — как в v1. Язык по умолчанию — `workflow.language` в
настройках (`en`). В ответах HTTP рядом с `title` есть `titleText` — текст на языке
запроса; у задач так же. `filter[folder]` берёт папку и всё, что ниже. Схема хранилища меняется → новое owned store
`bazis.workflow.definitions.v2` (префикс `bazis_wf2_def_`) с переносом данных
(§9).

### 4.2 Палитра как данные

`GET /workflow/palette`: виды узлов с ролью и JSON Schema их `config`, список
функций выражений с типами, системные пути, контракты Tools с `callers`
`workflow` (вход и выход в JSON Schema, `sideEffect`, `dryRun`, ссылки
`x-ref`). Дизайнер строит формы шагов по ней: новый Tool приложения
появляется в дизайнере без выпуска фреймворка.

### 4.3 HTTP

Маршруты v1 сохраняются; списки — JSON:API (`filter[folder]`, `filter[search]`,
`page[size]`, `page[number]`, `sort`). Добавляются: `POST /workflow/validate`
(проверка без сохранения), `GET /workflow/palette`, удаление процесса
(`DELETE`, только архивный, без живых экземпляров и без разделов:
`WorkflowPartitions.of(key)` пуст, иначе `409 in_use` — ничего не теряется
молча). Оптимистичная блокировка
черновика: `saveDraft(key, document, actor, { expected? })`, где `expected` —
`draftUpdatedAt` прочитанного черновика; иначе `409 conflict`. Ответ несёт новое
`draftUpdatedAt` для следующего сохранения. `filter[folder]` приходит с полем на
этапе 2, удаление — на этапе 4.

### 4.4 События для аудита

После успешного действия, после коммита: `WORKFLOW_PROCESS_CHANGED`
(`created` / `updated` / `draftSaved` / `published` / `archived` /
`restored` / `deleted`), `WORKFLOW_INSTANCE_STARTED`, `WORKFLOW_INSTANCE_CANCELLED`,
`WORKFLOW_INSTANCE_RETRIED`, `WORKFLOW_TASK_COMPLETED` — с актором, целью и
`request: { ip, userAgent } | null` (из HTTP; `null` для вызова из кода).
Журнал аудита пишет приложение. `deleted` приходит с удалением процесса (этап 4).

## 5. Исполнение (Runtime)

### 5.1 Запуски

- **Ручной**: `start(key, { input, partition, businessKey, actor, test? })`;
  `sameKey` и `maxConcurrent` проверяются в той же транзакции под
  блокировкой процесса (advisory lock по ключу). `queue` — экземпляр в
  статусе `pending`, стартует, когда освободится место.
- **Массовый**: `startMany(key, items: { input, businessKey }[], options)` —
  массовое действие над записями; каждый элемент — отдельный экземпляр,
  `businessKey` обязателен и подчиняется `sameKey`; ответ — по элементу
  `started | skipped | rejected` с причиной.
- **Расписание**: `cron`, `timezone` (IANA, по умолчанию UTC), `from?`,
  `until?`, `overlap: "skip" | "queue" | "parallel"`, `catchUp: boolean`
  (по умолчанию `false`, как в 0.128.0), `partitions: "none" | "all" |
  string[]` (по умолчанию `"none"`: один запуск без раздела). `"all"` —
  запуск в каждом включённом разделе из `WorkflowPartitions`, со своим
  часовым поясом раздела, если у узла его нет; разделов может быть тысячи,
  поэтому `"all"` выбирается явно, а запуски раздела идут пачками заданий.
- **Событие**: `eventStart` с `filter?: Expr` над `$event`,
  `debounce?: { key: Expr, window }` (частые события одного ключа сливаются в
  последнее), `delay?`, `ignoreOwn?: boolean` (не запускать, если событие
  вызвал экземпляр этого же процесса: `emit(…, { cause: { instanceId } })`).
  Раздел события: `eventStart` запускается только в разделе из
  `emit(…, { partition })` и только если `WorkflowPartitions` включает
  процесс в этом разделе; событие без раздела запускает только процессы без
  разделов.
- **Надёжная доставка события**: `emitLater(tx, eventKey, payload, options)`
  пишет задание `event` в хранилище исполнения в транзакции приложения `tx`
  через `tx.use(context, work)` (outbox; приложение и owned store на одном
  `DatabaseProvider`); воркер доставляет его как `emit`. Транзакция явная:
  неявная «текущая» сломалась бы, когда приложение пишет без
  `transactionScope`.

### 5.2 Ожидание

`eventWait` получает `until?: Expr` над `$event` — продолжить, только когда
условие истинно (ждать, пока запись станет «Одобрен»); остальные события
ключа оставляют шаг ждать. Срок ожидания — `boundaryTimer`, как в v1.

### 5.3 Экземпляр и журнал запусков

К экземпляру добавляются `test`, `parentInstanceId`, `status: "timedOut"`
(срок `runTimeout` вышел; `errorHandler` запускается), `failedNode`,
`durationMs` в ответах. Шаг с `timeout` — ошибка с причиной `timeout`. Список
экземпляров — JSON:API. Схема меняется → `bazis.workflow.runtime.v2`
(`bazis_wf2_run_`), задачи → `bazis.workflow.tasks.v2` (`bazis_wf2_task_`).

### 5.4 Пробный запуск

`start(…, { test: true })`. Tool с `dryRun: "supported"` вызывается с
`context.dryRun = true` и сам ничего не меняет; Tool без поддержки не
вызывается, шаг получает заглушку `{ dryRun: true }` и запись в истории.
Пробные экземпляры не публикуют события приложения (`WORKFLOW_TASK_REQUESTED`
и др.), задачи создаются с пометкой `test` и адресуются только тому, кто
запустил, — тест не засыпает входящие исполнителей. Пробные экземпляры
хранятся сутки; в списках скрыты по умолчанию, `filter[test]=true` их
показывает.

## 6. Порты для приложения

| Порт | Что даёт приложение | По умолчанию |
| --- | --- | --- |
| `WorkflowInputValidator` | Проверка значений по полям и их `extensions` (правила полей приложения) | Типы §3.4 |
| Виды ссылок (ACCESS-001 §6) | `@Module({ references })`: `exists`, `describe`, `search` для своих видов `x-ref`; обратный ход — `IWorkflowDefinitions.referencing(ref)` | `workflow.process`, `workflow.folder` объявляет `WorkflowModule`, `orm.entity`, `orm.field` — `ormEntityTools`; вид без владельца — ошибка старта |
| `WorkflowPartitions` | Разделы процесса (арендаторы, пространства, организации): `of(processKey)` → `{ partition, timezone?, enabled }[]` | Один раздел `null` |
| `WorkflowExtensions` | `namespaces()` и `check(namespace, value, target, context)` → список замечаний: проверка `extensions` своего пространства имён в корне, узлах, переменных | Пространств имён нет |
| `SecretStore` (`bazis/core/tools`) | Значения секретов по имени | Из конфигурации `secrets.*` |

Права — не порт процессов, а общий слой фреймворка (§6.2, [ACCESS-001](ACCESS.md)). Все порты получают контекст `{ partition, language, actor }`. Язык: в HTTP —
из `Accept-Language` среди языков `workflow.languages`, иначе
`workflow.language`; в событиях, расписании и фоне — `workflow.language`.

### 6.1 Контракт Tool (TOOLS-001, дополнение)

- `context.actor` в `execute(input, context)` — от чьего имени шаг (по
  `runAs`); поле `author` в данных процесса больше не нужно.
- `dryRun: "supported" | "unsupported"` в `@Tool` (по умолчанию
  `unsupported`).
- Персональные данные: `x-personal: true` у поля входа или выхода — значение
  маскируется исполнителем в истории и журнале при `log.maskPersonal`.
- Ссылки во входе: `x-ref: "<вид>"` в JSON Schema поля — значение поля
  ссылка (`dm.table`); `x-ref-keys: "<вид>"` у объекта — ссылки его ключи
  (`values` в `data.record-update`: ключи — поля таблицы). `x-ref-scope` —
  JSON Pointer на соседний вход, задающий область (`"x-ref-scope": "/table"`:
  поле ищется в таблице из входа `table`). В классе входа Tool это литералы
  `@Validator({ ref, refKeys, refScope })`: их читает генератор схем.
- `context.metadata` содержит `instanceId`, `processKey`, `nodeId`,
  `partition`, `test` — чтобы Tool мог передать `cause` в свои события.

### 6.2 Права ([ACCESS-001](ACCESS.md))

Своей системы прав и своего порта прав у процессов нет. `WorkflowModule`
объявляет каталог и виды ссылок, как любой модуль с действиями:

| Право | Что даёт | Раздел (`scope`) | Атрибуты (`on`) |
| --- | --- | --- | --- |
| `workflow.processes.read` | Каталог, версии, палитра, `validate` | `lookup`: разделы процесса из `WorkflowPartitions` | `process`, `folder` |
| `workflow.processes.manage` | Черновики, карточка, удаление | `"none"` | `process`, `folder` |
| `workflow.processes.publish` | Публикация; запуск от системного актора процесса (§3.5) | `"none"` | `process`, `folder` |
| `workflow.instances.start` | Ручной и массовый запуск | раздел запуска из запроса (`"request"`) | `process`, `folder` |
| `workflow.instances.read` | Экземпляры и журнал запусков; `owner: startedById` | `column: partition` | `process`, `folder`, `test` |
| `workflow.instances.manage` | Отмена, повтор, перенос | `column: partition` | `process`, `folder` |
| `workflow.events.emit` | `POST /workflow/events` | раздел события из запроса (`"request"`) | `event` |
| `workflow.tasks.work` | Задачи, адресованные субъекту или взятые им | `column: partition` | `process` |

- Каталог процессов (`manage`, `publish`) — без раздела: процесс один на
  приложение, подключение к разделам — через `WorkflowPartitions`.
- «Свои задачи» — не `own`: адресованные субъекту (по `principals`) или
  взятые им фреймворк считает сам; `owner` у задач нет.
- «Только свои экземпляры» — грант с условием `{ own: true }`; списки
  экземпляров и задач по всем разделам сразу фильтрует `Access.filter`.
- Адресаты задач — `AccessPolicy.principals` по разделам: открытая строка
  `<вид>:<id>` (`user:`, `role:`, у приложения свои виды), считаются при
  просмотре, а не при создании задачи.
- В фоне права не проверяются (ACCESS-001 §5): расписание, события,
  `callProcess`, `errorHandler`, шаги. Право дал тот, кто публиковал процесс
  и подключал его к разделу; Tools процесса `can` не вызывают.
- `folder` в списках экземпляров — `lookup`: папка → ключи её процессов.
- Каталог растёт вместе с этапами §10: этап 0 объявляет права без того, чего
  ещё нет. `folder` и вид ссылки `workflow.folder` появляются с карточкой
  (этап 2), раздел `workflow.processes.read` из `WorkflowPartitions` — на
  этапе 4 (до него право без раздела: это и есть значение порта по умолчанию,
  один раздел `null`), `test` — с пробным запуском (этап 5). Части модуля
  объявляют каждая свои права: приложение может подключить не все части.

### 6.3 Проверка ссылок

При публикации и в `bazis workflow check`: каждое литеральное значение поля с
`x-ref` проверяется владельцем вида ссылки (ACCESS-001 §6); нет — замечание `broken_ref` с узлом. Выражения
проверяются только при исполнении (причина ошибки `ref_not_found`).
`referencing(ref)` по последним опубликованным версиям отвечает, кто
ссылается на поле или таблицу, — приложение запрещает или предупреждает
при архивации.

## 7. Стандартные Tools: `bazis/core/tools`

Необязательный модуль `StandardToolsModule`; `callers` задаются настройкой
(процессы, агенты).

### 7.1 `http.request`

Метод, URL, заголовки, тело JSON, авторизация (`none`, `bearer`, `basic`,
`apiKey` — значения из `$secrets`), коды успеха, `saveTo`. Защита закрыта по
умолчанию: пустой `tools.http.allow` — запросы никуда; после DNS проверяется
IP, частные, loopback и link-local адреса запрещены; редиректы — только
внутри списка; лимиты на размер ответа (1 МБ) и время; `dryRun: "supported"`
только для `GET` и `HEAD`.

### 7.2 Секреты

`$secrets.NAME` подставляет исполнитель Tools, а не Tool. Значение
регистрируется в редакции вызова (`bazis/library/redaction`) и вырезается
из истории, выхода шага, журнала и ошибок. В документ попадает только имя.

### 7.3 Уведомления

Стандартный Tool только для каналов, которые есть во фреймворке; иначе —
событие процесса, доставку делает приложение.

### 7.4 Данные: `ormEntityTools`

```ts
@Module({ tools: [...ormEntityTools(Order, { context: OrdersDbContext, ops: ["find", "create", "update"], fields: ["status", "amount"] })] })
```

Делает Tools `orm.<entity>.find|create|update|delete` с фильтром по
разрешённым полям, лимитом, сортировкой, защитой от массовых изменений и
`dryRun: "supported"` (проверка без записи); входы помечены `x-ref` вида
`orm.field`. Приложение решает, какие сущности и поля открыты процессам;
ничего не открыто само. `partitionField` (например, `organizationId`)
привязывает Tools к разделу: каждый запрос фильтруется по `$run.partition`,
создание записывает его в поле; без раздела у экземпляра такие Tools
отказывают. Иначе процесс одного арендатора видел бы и менял записи другого.

## 8. Пример потребителя: что делает bazis-cms

CMS — пример того, как приложение подключает процессы через Tools и порты
§6; ничего из этого фреймворк не требует.


- Tools Data Manager: `data.record-get/create/update` (есть),
  `data.records-find/update-many/delete` с фильтром DM `filter[field][op]`,
  лимитом и защитой от массовых изменений; `dryRun: "supported"`; `x-ref` на
  таблицы и поля.
- События записей DM через `emitLater` в транзакции записи, с `cause` из
  `context.metadata`; защита от лавины — `ignoreOwn` и `debounce` процесса.
- Права (ACCESS-001 §9): модуль ролей CMS реализует `AccessPolicy` и
  показывает каталог всех модулей, включая `workflow.*`; проверка маршрутов
  приложения — вид токена, живая сессия, блокировка; админ CMS — `"all"`.
  `CmsWorkflowAccess` удаляется. Пока модуля ролей нет, `AccessPolicy` CMS
  отдаёт гранты по видам токена, `starters` пространства — грант с
  `where: { process: { in: […] } }`.
- Порты: `DmWorkflowInputValidator` (есть,
  правила DM переходят из ключей поля в `extensions.cms`),
  виды ссылок `dm.table`, `dm.field` (запись DM несёт раздел своего
  создания), `WorkflowPartitions`
  (`wf_space_processes` переносится на порт; часовой пояс и включённость —
  колонки связи, пока нет модуля пространств), `WorkflowExtensions`
  (`cms`: места кнопок запуска, правила полей), секреты — своё хранилище или
  конфигурация.
- `RecordsService` пишет в явном `transactionScope` и вызывает
  `emitLater(tx, …)`; `cause` из `context.metadata` идёт в `RecordsContext`.
- `dryRun` для DM: `create` и `update` делают только `records.validate` и
  возвращают запись, которая получилась бы.
- e2e CMS обновляются на каждом этапе фреймворка.
- Дизайнер-конструктор по палитре; места кнопок запуска (карточка записи,
  список, массовое действие); свой аудит по событиям §4.4.
- `author` в Tools записей — необязательное переопределение `context.actor`
  (решение владельца, §11.1).

## 9. Хранилища и переход

Схемы трёх частей меняются, поэтому три новых owned store (`…definitions.v2`,
`…runtime.v2`, `…tasks.v2`, префиксы `bazis_wf2_def_`, `bazis_wf2_run_`,
`bazis_wf2_task_`). Они появляются на этапе 2 сразу с колонками этапов 3–5: `test`,
`parentInstanceId`, `parentTokenId` у экземпляра, `parentTokenId`, `iteration`,
`locals` у токена, `payload`, `dedupeKey`, `partition`, `nodeId` у задания, `test` у
задачи. Иначе каждый этап требовал бы своего хранилища. Изменить хранилище на месте нельзя по устройству owned
store («миграций для хранилищ нет»), поэтому префиксы с номером остаются;
это цена гарантии, что таблицы модуля никто не меняет. Выпуск переносит процессы и версии v1 при
старте, один раз, если новый каталог пуст: документы через `upgradeDocument`,
карточки (`title` → язык по умолчанию), даты сохраняются. Экземпляры v1 не переносятся: в проде их нет; живые тестовые
экземпляры завершают на старом выпуске. Старые таблицы `bazis_wf_def_`,
`bazis_wf_run_`, `bazis_wf_task_` удаляются вручную по `upgrading.md`.
Процессы в коде (`defineProcess`) принимают v2; v1 переводится
`upgradeDocument`.

## 11. Решено на рецензии и открыто

Решено на этапе 3 (v1.11):

- **Экземпляры не ждут друг друга.** Транзакция держит строку одного экземпляра;
  что касается другого, идёт заданием в той же транзакции (`call`, `returned`,
  `cancelChildren`, `release`, `errorHandler`). Вызов вложенного процесса — тоже
  задание, как инструмент: вход проверяется вне транзакции, портом приложения.
- **Упавший вызванный.** Вызвавший получает ошибку сразу (`child_failed`), повторяют
  вызвавшего, а он продолжает того же вызванного: заново запускать нельзя, у новых
  токенов другие ключи идемпотентности. Прямой `retry` вызванного отклоняется.
- **`maxConcurrent` сверх предела — `pending`, не отказ**, при любом способе запуска:
  предел не должен терять запуски по событию и расписанию. `failed` места не занимает.
- **`sameKey` смотрит на незавершённые**: `pending`, `running`, `failed`. `skip` при
  ручном запуске — 409, в `startMany` и `emit` — запись в ответе.
- **`timedOut` — конец**, повторить нельзя; у `failed` срок ждёт повтора, иначе
  обработчик ошибки запустился бы дважды.
- **Обработчик ошибки не запускает обработчик**, цепочка конечна. Глубина вызовов — 16.
- **Партии цикла**: транзакция начинает до 100 итераций, дальше задание `loop`.
- **Хранилище не меняется**: всё легло в заложенные на этапе 2 колонки и статусы-строки.
- Попутно исправлено: при повторе теряли ход задания параллельных ветвей, сброшенные
  воркером, пока экземпляр стоял, и токены, не успевшие двинуться; следующая задача
  сразу за выполненной падала на конфликте контекста ORM (`insertIfAbsent` вместо
  отслеживания); вывод задачи теперь берётся из её токена.

Решено агентами (v1.1–1.2): общая транзакция для `emitLater` — `tx.use`
(§5.1); явный часовой пояс узла расписания важнее часового пояса раздела;
`queue` — статус `pending`; пробные запуски хранятся сутки и скрыты в
списках по умолчанию; новые хранилища вместо изменения на месте (§9);
персональные данные — `personal` у переменных и `x-personal` в схемах входа
и выхода Tool, маскирует исполнитель; два порта: `WorkflowExtensions`
проверяет форму `extensions` при сохранении, `WorkflowInputValidator` —
значения при запуске и в задачах. Решено в v1.5–1.6 (по вопросам владельца):
права на процессы — каталог permissions в общем слое прав фреймворка
[ACCESS-001](ACCESS.md), без своей системы ролей и без порта с условиями в
коде приложения (§6.2).

Решено владельцем 2026-11-01:

1. **Автор записи.** `context.actor` по `runAs` — автор по умолчанию; в
   Tools записей CMS остаётся необязательное поле `author` для случая «кто
   создал — решается переменными процесса».

2. **Готовые экраны дизайнера.** Во фреймворке их нет: ядро дизайнера
   (§3.8) — во фреймворке, экраны каждое приложение рисует само поверх ядра;
   CMS — в своей админке. Экраны как UI-профиль `WorkflowModule` можно
   вернуть к обсуждению, когда у `bazis/library/ui` появится отрисовка.
