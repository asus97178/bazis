# Архитектура модулей

Как разбить приложение на модули, когда хватит одного модуля, а когда
нужен составной, что кладёт в модуль CLI и зачем каждому модулю паспорт
`MODULE.md`. Это короткая версия архитектурной спецификации bazis; полный
текст лежит в каждом проекте, созданном `bazis new`, —
`docs/architecture/MODULE_ARCHITECTURE.md`.

Все команды проверены на bazis 0.97.8.

## Атомарный модуль

**Одна функция — один модуль.** Задачи, гости, рассылки — каждая функция
живёт в своём модуле и владеет всем, что ей нужно: моделями и контекстом
базы данных, сервисами, контроллерами, моделями запросов, фоновыми
службами, AI-инструментами.

«Атомарный» не значит маленький: в модуле может быть много файлов,
несколько контроллеров и таблиц, зависимости от других модулей. Важно
другое — у модуля одна ответственность и один хозяин данных.

Чего **не** делать:

- делить функцию по слоям: «модуль контроллеров», «модуль сервисов»,
  «модуль моделей»;
- заводить новый модуль только потому, что добавился контроллер,
  фоновая служба или второй контекст базы данных;
- считать модуль составным из-за `imports`: зависимость от `AuthModule`
  или кэша — это просто зависимость.

## Составной модуль

Составной модуль (пакет, `pack`) нужен, когда внутри большой области есть
**несколько независимых функций** — у каждой свои данные, свои операции и
свои тесты. Пример — каталог с товарами и категориями или конструктор
данных с таблицами, полями, валидаторами и записями.

Корень пакета только собирает части:

```ts
@Module({
  imports: [ItemsModule, CategoriesModule, PricesModule],
  exports: [],
})
export class CatalogModule {}
```

В корне нет своих сервисов, контроллеров, моделей и фоновых служб — всё
это принадлежит частям. Если частям нужна общая координация, у неё тоже
должен быть свой атомарный модуль-владелец, а не скрытый сервис в корне.
Наружу корень может отдать токены частей —
[реэкспортом](encapsulation.md#реэкспорт).

Если части различаются только названиями слоёв, пакет не нужен — это один
атомарный модуль.

## Как выбрать

| Ситуация | Решение |
| --- | --- |
| Задачи: создать, прочитать, сменить статус | Атомарный модуль |
| Гости: регистрация и учёт | Атомарный модуль |
| В модуль добавился контроллер, фоновая служба, второй контекст БД | Остаётся атомарным |
| Каталог: товары, категории, цены со своими данными | Составной, если части действительно независимы |
| Большая область, но всё крутится вокруг одной сущности | Атомарный модуль |

По умолчанию новая функция — атомарный модуль. Рост кода — повод
пересмотреть границы, но не обязанность делить.

## Создание: только через CLI

Модули создаются командами CLI — так у них сразу правильная раскладка,
паспорт и подключение. Вручную каркас модуля не пишут и соседний модуль не
копируют.

| Что нужно | Команда |
| --- | --- |
| Атомарный модуль без кода | `bunx bazis g module Mailer --empty` |
| Атомарный модуль с учебным CRUD | `bunx bazis g module Task` (или `--minimal`) |
| То же плюс кэш, авторизация, фоновая служба, AI-инструмент | `bunx bazis g module Task --full` |
| Составной модуль | `bunx bazis g pack Catalog --parts items,categories` |
| Новая часть существующего составного | `bunx bazis g module Prices --empty --pack Catalog` |

Каждая команда подключает модуль: атомарный и составной — в `imports`
корневого `AppModule`, новую часть — в корень своего пакета. Затем
запускается codegen. Посмотреть план без записи файлов — `--dry-run`.

`--minimal` и `--full` создают пример CRUD с базой данных. Его поля —
образец, а не требования: замените их под свою функцию. Чтобы такой модуль
запустился, приложению нужна база данных, а модулю `--full` ещё и кэш
(`runApp(AppModule, { cache: memory() })`). Для первой функции без базы
берите `--empty`.

## Что создаёт CLI

Атомарный модуль, `g module Task`:

```text
task/
├── MODULE.md                          паспорт
├── Task.module.ts                     точка подключения
├── model/
│   ├── Task.model.ts                  сущность ORM
│   └── Task.dbContext.ts              контекст базы данных
├── services/
│   ├── ITask.service.ts               контракт сервиса (абстрактный класс)
│   └── Task.service.ts                реализация
└── http/
    ├── Task.controller.ts             HTTP-входы
    └── contracts/
        ├── Task.requests.ts           модели запросов
        ├── Task.responses.ts          модели ответов
        └── TaskList.query.ts          что можно фильтровать и сортировать в списке
```

Составной модуль, `g pack Catalog --parts items,categories`, и часть,
добавленная потом через `--pack`:

```text
catalog_modules/
├── MODULE.md                          паспорт пакета: части и связи между ними
├── Catalog.module.ts                  корень: только imports
├── items_module/
│   ├── MODULE.md
│   └── Items.module.ts
├── categories_module/
│   ├── MODULE.md
│   └── Categories.module.ts
└── prices_module/                     добавлена: g module Prices --empty --pack Catalog
    ├── MODULE.md
    └── Prices.module.ts
```

Остальные папки появляются, только когда в них есть код: `background/` —
фоновые службы, `ai/` — инструменты для агентов, `events/` — события,
`config/` — настройки модуля, `errors/` — доменные ошибки, `internal/` —
закрытые детали, `test/` — тесты. Пустые папки «на будущее» не создают.

## Паспорт `MODULE.md`

Паспорт — короткое описание модуля для людей и для AI-агентов, которые
работают с кодом: за что модуль отвечает, что у него внутри, какие у него
входы и что проверено. CLI создаёт паспорт с каркасом и честным статусом:

```text
# PricesModule

Passport version: 1.0. Type: atomic, a part of the composite CatalogModule ([passport](../MODULE.md)). CLI profile: empty.
Status: scaffold generated; the domain implementation and checks are not done.
Entry: [Prices.module.ts](Prices.module.ts), class PricesModule, no arguments.
Created with: `bunx bazis g module Prices --empty --pack Catalog`.
```

Строку `Created with` CLI записывает сам — по ней видно, каким профилем и
куда модуль создавался.

Дальше паспорт заполняет автор, вместе с кодом:

| Раздел | Что записать |
| --- | --- |
| Ответственность | Какую функцию решает модуль, какими данными владеет |
| Состав | Компоненты, их файлы, зависимости и экспорт |
| Входы | Каждый HTTP-маршрут, публичный метод сервиса, инструмент, событие: поля, типы, обязательность, проверки, результат, ошибки |
| Проверки | Что проверено и чем; что не проверено |

У составного модуля паспорт пакета описывает части и связи между ними.
Часть, добавленную через `--pack`, впишите в таблицу частей сами — CLI
напомнит об этом.

Паспорт обновляют в той же задаче, что и код: изменились поля модели
запроса, добавился маршрут — поменялся и паспорт.

## Правила между модулями

- Зависимости между модулями — только через `imports` и `exports`.
  Граф модулей не должен содержать циклов.
- У каждой сущности ORM, контекста и фонового обработчика один модуль-
  владелец. Зависимость от чужого сервиса не делает вас владельцем его
  таблиц.
- Общие подключения — база данных, кэш — создаёт инфраструктура (`infra`
  в `runApp`); модуль получает их через DI и не открывает свой пул.
- Не обходите публичный API модуля: не импортируйте его приватные файлы
  и контексты базы данных напрямую.
