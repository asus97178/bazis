# Фильтры запросов и мягкое удаление

Некоторые строки приложение не должно видеть почти никогда: удалённые
записи, архив, данные другой организации. Условие для них ставится один
раз — на сущность, — и bazis добавляет его в каждый запрос к ней.

- `@SoftDelete()` — мягкое удаление: `remove()` ставит время удаления
  вместо `DELETE`, а запросы такие строки не видят.
- `@QueryFilter(...)` — своё условие для всех запросов к сущности.
- `ignoreQueryFilters()` — снять оба вида условий в одном запросе.

Все примеры проверены на bazis 0.115.0 и PostgreSQL 17.

## Мягкое удаление

```ts
import { Column, Entity, Key, Required, SoftDelete } from "bazis/core/orm";

@Entity({ table: "notes" })
export class Note {
  @Key() id = 0;
  @Required() @Column({ type: "text" }) text = "";
  @SoftDelete() deletedAt: Date | null = null;
}
```

`@SoftDelete()` сам объявляет столбец — `@Column` не нужен. Столбец
допускает `NULL`: `NULL` значит «не удалена».

```text
CREATE TABLE "public"."notes" ("id" bigint GENERATED BY DEFAULT AS IDENTITY NOT NULL, "text" text NOT NULL, "deletedAt" timestamptz, …)
```

Удаляют как обычно — `remove()` и `saveChanges()`:

```ts
const note = await this.db.notes.find(id);
this.db.notes.remove(note!);
await this.db.saveChanges();
```

```text
UPDATE "notes" SET "deletedAt" = $1 WHERE "id" = $2   ['2026-10-22 22:16:40.313+00', '1']
```

Строка остаётся в таблице, а у объекта `note.deletedAt` — время удаления.

### Удалённые строки не видны

Условие `"deletedAt" IS NULL` попадает во все чтения: `where`, `find`,
`count`, `first`, `include`.

```ts
await this.db.notes.orderBy((n) => n.id).toList();   // ["b"] — "a" удалена
await this.db.notes.find(1);                         // null
await this.db.notes.count();                         // 1
```

```text
SELECT "id", "text", "deletedAt" FROM "notes" WHERE "deletedAt" IS NULL ORDER BY "id" ASC
SELECT "id", "text", "deletedAt" FROM "notes" WHERE "deletedAt" IS NULL AND "id" = $1 LIMIT $2
SELECT COUNT(*) AS count FROM "notes" WHERE "deletedAt" IS NULL
```

Сервис, который отвечает `404` на `find(id) === null`, отвечает `404` и
на удалённую запись — отдельной проверки не нужно.

### Корзина и восстановление

Удалённые строки видны после `ignoreQueryFilters()`:

```ts
// Все строки, и удалённые тоже
await this.db.notes.ignoreQueryFilters().toList();

// Только удалённые — корзина
await this.db.notes
  .ignoreQueryFilters()
  .where((n) => n.deletedAt.isNotNull())
  .toList();
```

```text
SELECT "id", "text", "deletedAt" FROM "notes"
SELECT "id", "text", "deletedAt" FROM "notes" WHERE "deletedAt" IS NOT NULL
```

Восстановить — вернуть `NULL` и сохранить:

```ts
const note = await this.db.notes
  .ignoreQueryFilters()
  .where((n) => n.id.eq(id))
  .first();
note!.deletedAt = null;
await this.db.saveChanges();
```

```text
UPDATE "notes" SET "deletedAt" = $1 WHERE "id" = $2   [NULL, '1']
```

### Удалить окончательно

`remove()` удалённой строки не стирает её, а ставит новое время
удаления. Окончательно удаляет `executeDelete()` — сразу, одним
`DELETE`:

```ts
await this.db.notes
  .asNoTracking()
  .ignoreQueryFilters()
  .where((n) => n.id.eq(id))
  .executeDelete();
```

```text
DELETE FROM "notes" WHERE "id" = $1
```

Без `ignoreQueryFilters()` `executeDelete()` стирает только ещё не
удалённые строки. Подробнее — в главе
[Немедленные изменения](immediate.md#мягкое-удаление-и-фильтры).

### Своё имя столбца

Столбец можно объявить самому и назвать его в `@Entity`:

```ts
@Entity({ table: "lists", softDelete: "removedAt" })
export class List {
  @Key() id = 0;
  @Required() @Column({ type: "text" }) name = "";
  @Column({ type: "datetime" }) removedAt: Date | null = null;
}
```

Работает так же, как `@SoftDelete()` на поле:
`UPDATE "lists" SET "removedAt" = $1 …`.

### Связи

Удалённые сущности не попадают и в `include`:

```ts
await this.db.lists.include((l) => l.items).toList();
// "home": ["milk"] — "bread" удалён
```

```text
SELECT "id", "listId", "title", "deletedAt" FROM "items" WHERE "deletedAt" IS NULL AND "listId" IN ($1)
```

- Удаление не распространяется на связанные строки. Мягко удалённый
  список оставляет свои пункты, и у них `include((i) => i.list)` даёт
  `null`. Удалите детей вместе с родителем сами — в одной
  [транзакции](transactions.md), например через
  `executeUpdate({ deletedAt: new Date() })`.
- `ignoreQueryFilters()` снимает условия и со связей из `include`: в
  корзине списка видны и его удалённые пункты (с версии 0.114.0; раньше
  связи фильтровались всё равно).

### Уникальные индексы

Мягко удалённая строка по-прежнему занимает своё значение в уникальном
индексе. Удалили пользователя `ann@x.io` и создали заново — сохранение
откажет:

```text
UniqueViolationError: Unique constraint "ix_users_email" violated.
```

Сделайте индекс частичным — условие `where` оставит в нём только
неудалённые строки:

```ts
@Entity({ table: "users" })
@Index<User>(["email"], { unique: true, where: (u) => u.deletedAt.isNull() })
export class User {
  @Key() id = 0;
  @Required() @Column({ type: "text" }) email = "";
  @SoftDelete() deletedAt: Date | null = null;
}
```

```text
CREATE UNIQUE INDEX "ix_users_email" ON "public"."users" ("email") WHERE "deletedAt" IS NULL
```

- Удалённый `ann@x.io` больше не мешает: новый пользователь с тем же
  адресом сохраняется. Два **неудалённых** с одним адресом — по-прежнему
  `UniqueViolationError`.
- В `where` — те же операторы, что в
  [`@Check`](entities.md#индексы-и-проверки). Сравнивать дату с
  литералом нельзя — только `isNull()`, `isNotNull()` или другой столбец.
- `ensureCreated` добавит индекс и к уже существующей таблице, а при
  каждом запуске сверяет условие с базой. Изменили `where` — запуск
  остановится (`partial index condition (where) differs`): поменяйте
  индекс [миграцией](schema.md).
- Частичные индексы — с версии 0.115.0; в
  [owned stores](owned-stores.md) их нет.

## Свой фильтр

`@QueryFilter` добавляет условие ко всем запросам сущности:

```ts
import { Column, Entity, Key, QueryFilter, Required, SoftDelete } from "bazis/core/orm";

@Entity({ table: "posts" })
@QueryFilter<Post>((p) => p.archived.eq(false))
export class Post {
  @Key() id = 0;
  @Required() @Column({ type: "text" }) title = "";
  @Column({ type: "boolean" }) archived = false;
  @SoftDelete() deletedAt: Date | null = null;
}
```

```ts
await this.db.posts.toList();                        // ["live"]
await this.db.posts.ignoreQueryFilters().toList();   // ["live", "old"]
```

```text
SELECT "id", "title", "archived", "deletedAt" FROM "posts" WHERE "archived" = $1 AND "deletedAt" IS NULL   [false]
SELECT "id", "title", "archived", "deletedAt" FROM "posts"
```

- Несколько `@QueryFilter` и `@SoftDelete` складываются через `AND`.
- Фильтр действует в запросах, `find`, `count`, `include` и
  [немедленных изменениях](immediate.md).
- `ignoreQueryFilters()` снимает **все** условия сразу — и `@QueryFilter`,
  и мягкое удаление. Снять только одно нельзя: нужное условие допишите в
  `where`.
- Фильтр с одним параметром вычисляется один раз, при объявлении класса.
  Значение, которое меняется, — время, пользователь, организация, — так не
  передать.

### Фильтр с контекстом

Фильтр с двумя параметрами получает `DbContext` **каждого запроса** и
вычисляется заново:

```ts
@QueryFilter<Note, NotesDb>((n, db) => n.tenantId.eq(db.tenantId))
```

Так строится разделение данных между организациями: каждый запрос сам
получает условие по организации текущего пользователя. Полный пример —
в главе [Шаблоны авторизации](../security/authorization-patterns.md).
