# Модули

Модуль — класс с декоратором `@Module`, который собирает всё, что нужно одной
функции приложения: сервисы, контроллеры, настройки, фоновые службы. Модуль
решает, что из этого видно другим модулям.

```ts
import { Module, scoped } from "bazis/core/di";

@Module({
  imports: [AuthModule],
  config: taskConfig,
  providers: [scoped(TaskService)],
  controllers: [TaskController],
  exports: [TaskService],
})
export class TaskModule {}
```

## Корневой модуль

Приложение — дерево модулей. Корень — `AppModule` в
`src/app/modules/App.module.ts`, его передают в `runApp`:

```ts
@Module({ imports: [GreetingModule, TaskModule], exports: [] })
export class AppModule {}
```

Корень только собирает функции через `imports` и не содержит своей логики.
Команда `bunx bazis g module <Имя>` сама добавляет новый модуль в `imports`
корня.

## Поля `@Module`

| Поле | Что в нём | Пример |
| --- | --- | --- |
| `imports` | Модули, от которых зависит этот | `[AuthModule]` |
| `providers` | Сервисы модуля и их время жизни | `[scoped(TaskService)]` |
| `controllers` | HTTP-контроллеры. Регистрировать их в `providers` не нужно | `[TaskController]` |
| `exports` | Что доступно модулям, которые импортируют этот | `[TaskService]` |
| `config` | Объявления настроек модуля (`defineConfig`) — одно или массив | `taskConfig` |
| `background` | Фоновые службы с управляемым запуском и остановкой | `[ReportScheduler]` |
| `ormBazis` | Контекст базы данных и сущности модуля | `{ context: TaskDbContext, entities: [Task] }` |
| `grpcControllers` | gRPC-контроллеры | `[TaskGrpcController]` |
| `tools`, `agents`, `prompts` | Инструменты и агенты для AI | `[TaskSummaryTool]` |
| `uiProfiles` | Описания интерфейса для генерируемого UI (`defineUiProfile`) | `[taskUiProfile]` |
| `configure` | Регистрация провайдеров кодом — для редких случаев | `(di) => { ... }` |

Все поля необязательны. `ormBazis`, `grpcControllers` и поля для AI —
расширения: они работают, когда подключены соответствующие части фреймворка
(`bazis/core/orm`, `bazis/core/grpc`, `bazis/core/agent`).

## Что видно другим модулям: `exports`

Модуль `B` может внедрить сервис модуля `A`, только если выполнены оба
условия: `B` импортирует `A`, и `A` отдаёт этот сервис наружу.

| Как объявлен `exports` у модуля `A` | Что получат модули, импортирующие `A` |
| --- | --- |
| `exports: [TaskService]` | Только `TaskService` |
| `exports: []` | Ничего: все провайдеры `A` приватные |
| Поле не указано | Всё, что зарегистрировано в `A` |

Указывайте `exports` всегда — CLI так и создаёт модули. Модуль без `exports`
открыт целиком, и его внутренние сервисы незаметно становятся чужим API.

Нарушение границ останавливает запуск:

```text
Module "OtherModule": "OtherController" depends on "TaskService",
which is provided by another module but not exported.
```

Такая ошибка бывает в двух случаях: сервиса нет в `exports` своего модуля
**или** модуль-потребитель не добавил этот модуль в `imports` (текст ошибки
пока говорит только о первом).

`exports` ограничивает только внедрение зависимостей. Контроллеры, фоновые
службы и инструменты модуля работают в любом случае — доступ к ним
настраивается отдельно, например через `@Authorize`.

## Глобальные модули

Модуль с декоратором `@Global()` отдаёт свои `exports` всем модулям
приложения без `imports`:

```ts
import { Global, Module, singletonValue } from "bazis/core/di";

@Global()
@Module({ providers: [singletonValue(CLOCK, systemClock)], exports: [CLOCK] })
export class ClockModule {}
```

Так устроена инфраструктура: подключения к базе, кэш, логгер. Для обычных
функций приложения `@Global()` не используйте — явные `imports` показывают,
кто от кого зависит.

## Как создавать модули

Новые модули создаются только командой CLI — так у них сразу правильная
структура, паспорт `MODULE.md` и подключение к корню:

| Команда | Что создаёт |
| --- | --- |
| `bunx bazis g module Task --empty` | Пустой модуль и паспорт |
| `bunx bazis g module Task` или `--minimal` | Учебный CRUD: модель, контекст БД, сервис, контроллер, модели запросов |
| `bunx bazis g module Task --full` | То же плюс кэш, авторизация, фоновая служба и AI-инструмент |
| `bunx bazis g pack Catalog --parts items,categories` | Составной модуль из нескольких независимых частей |

## Один модуль или несколько

**По умолчанию одна функция — один модуль**, даже если в нём есть модель,
сервис, контроллер, фоновая служба и AI-инструмент. Технические слои
(«модуль контроллеров», «модуль сервисов») отдельными модулями не делают.

Составной модуль нужен, когда внутри действительно несколько независимых
функций со своими данными и ответственностью — например, каталог с товарами
и категориями. Его корень только собирает части через `imports`, а вся
логика живёт в частях. Подробнее — в разделе «Архитектура модулей».

## Структура папок модуля

CLI раскладывает модуль так; лишних папок не создавайте — каждая появляется,
только когда в ней есть код:

```text
task/
├── MODULE.md                 паспорт: ответственность, входы, зависимости
├── Task.module.ts            точка подключения модуля
├── model/                    сущности и контекст базы данных
├── services/                 бизнес-логика и интерфейсы сервисов
├── http/                     контроллеры
│   └── contracts/            модели запросов и ответов
├── background/               фоновые службы
├── ai/                       инструменты для агентов
└── test/                     тесты модуля
```
