# Модули

**Одна функция — один модуль.** HTTP API, данные, фоновые задачи, бизнес-процессы и AI-инструменты лежат рядом, в одной папке. А bazis следит, чтобы модули не брали друг у друга то, что им не отдавали: нарушение границы остановит запуск и подскажет, как его исправить.

Модуль — основа архитектуры bazis. Он объединяет всё, что относится к одной функциональности приложения, управляет её зависимостями и решает, что из неё доступно другим частям приложения.

Например, модуль пользователей содержит всё для работы с пользователями: создание и изменение данных, HTTP API, доступ к базе данных, фоновые процессы и инструменты для AI-агентов.

А создаётся модуль одной командой:

```bash
bunx bazis g module User
```

## Создание модуля

Модуль объявляется декоратором `@Module`. В нём собираются компоненты функциональности и связи с другими модулями.

```ts
import { Module, scoped } from "bazis/core/di";

@Module({
  imports: [AuthModule],                         // от каких модулей зависит
  providers: [scoped(IUserService, UserService)], // сервисы и их жизненный цикл
  controllers: [UserController],                 // HTTP API
  exports: [IUserService],                       // что модуль отдаёт другим
})
export class UserModule {}
```

`UserModule` объединяет HTTP-контроллер и сервис с бизнес-логикой пользователей. Он пользуется авторизацией из `AuthModule` и отдаёт другим модулям контракт `IUserService`.

Контракт — абстрактный класс с методами сервиса, а `UserService` — его реализация. Другие модули зависят только от контракта, поэтому реализацию можно заменить, не трогая их. CLI создаёт модули именно так.

bazis не заставляет делить код на технические слои. Контроллер, сервис и модель одной функции живут в одном модуле.

## Возможности модуля

Все поля `@Module` необязательны: модуль берёт только то, что ему нужно.

| Поле | Назначение |
|---|---|
| `imports` | Модули, от которых зависит текущий |
| `providers` | Сервисы и другие компоненты в DI |
| `controllers` | HTTP-контроллеры |
| `exports` | Что модуль отдаёт другим модулям |
| `config` | Настройки модуля, объявленные через `defineConfig` |
| `background` | Фоновые службы с управляемым запуском и остановкой |
| `ormBazis` | Контекст базы данных модуля |
| `gateways` | WebSocket-шлюзы |
| `grpcControllers` | gRPC-контроллеры |
| `httpClients`, `grpcClients` | Клиенты к внешним HTTP- и gRPC-сервисам |
| `processes` | Бизнес-процессы, описанные в коде |
| `permissions`, `roles`, `references` | Права доступа, роли по умолчанию и справочники для админки |
| `tools` | Инструменты, доступные AI-агентам |
| `agentToolHooks` | Хуки вокруг вызовов AI-инструментов: разрешить вызов, записать исход, собрать метрики |
| `uiProfiles` | Описания интерфейса для генерируемого UI (`defineUiProfile`) |
| `configure` | Программная настройка DI для особых случаев |

Базу данных, gRPC, бизнес-процессы, права и AI модуль получает, когда в приложении подключены соответствующие части фреймворка: `bazis/core/orm`, `bazis/core/grpc`, `bazis/core/workflow`, `bazis/core/access`, `bazis/core/agent`.

Модуль может начинаться с простого HTTP API и сервиса. Базу данных, фоновые службы, WebSocket, бизнес-процессы или AI-инструменты вы добавите, когда они понадобятся, в тот же модуль:

```ts
@Module({
  imports: [AuthModule],
  config: userConfig,
  providers: [scoped(IUserService, UserService)],
  controllers: [UserController],
  exports: [IUserService],
  ormBazis: { context: UserDbContext },
  background: [UserCleanupScheduler],
  gateways: [UserGateway],
  tools: [UserSummaryTool],
})
export class UserModule {}
```

## Приложение как набор модулей

Приложение bazis строится из модулей. Каждый отвечает за свою функциональность, а корневой модуль собирает их вместе.

Например, пользователи, авторизация, каталог, уведомления и отчёты — пять модулей, подключённых в `AppModule`:

```ts
@Module({
  imports: [UserModule, AuthModule, CatalogModule, NotificationModule, ReportModule],
  exports: [],
})
export class AppModule {}
```

Корневой модуль не содержит бизнес-логики. Он только определяет, из чего состоит приложение.

Корневой модуль лежит в `src/app/modules/App.module.ts` и подключается в `src/app/App.ts` декоратором `@App`. Новый модуль, созданный через CLI, сам добавляется в его `imports`.

## Границы модулей: что доступно другим

Модули в bazis не просто раскладывают код по папкам. Они контролируют, как функциональные части взаимодействуют друг с другом.

Модуль может использовать сервис другого модуля, только если выполнены два условия:

1. Он подключил модуль-источник через `imports`.
2. Модуль-источник отдал этот сервис через `exports`.

`UserModule` отдаёт `IUserService`:

```ts
@Module({
  providers: [scoped(IUserService, UserService)],
  exports: [IUserService],
})
export class UserModule {}
```

Теперь `ReportModule` может им пользоваться, если подключит `UserModule`:

```ts
@Module({
  imports: [UserModule],
  providers: [scoped(IReportService, ReportService)],
  exports: [IReportService],
})
export class ReportModule {}
```

Зависимости между модулями становятся явными. Если `exports` указан, модуль не сможет случайно взять внутренний сервис другого модуля, который тот не отдавал.

### Что можно экспортировать

| `exports` | Результат |
|---|---|
| `exports: [IUserService]` | Другим модулям доступен только `IUserService` |
| `exports: []` | Другие модули не получают ничего |
| `exports` не указан | Другим модулям доступно всё, что зарегистрировано в модуле |

**Всегда указывайте `exports` явно.** Так публичный интерфейс модуля под контролем, а его внутренние сервисы не становятся неофициальными зависимостями других частей приложения. CLI создаёт модули с `exports`.

Если граница нарушена, bazis остановит запуск и скажет, что не так и как это исправить. Например, `ReportService` берёт `Clock`, а `ClockModule` не подключён:

```text
Module "ReportModule": "ReportService" depends on "Clock", which module "ClockModule"
exports, but "ReportModule" does not list "ClockModule" in its imports.
Add "ClockModule" to the imports of "ReportModule".
```

Или `UserModule` подключён, но нужный сервис не отдаёт:

```text
Module "ReportModule": "ReportService" depends on "IUserService", which module
"UserModule" provides but does not export. Add it to the exports of "UserModule".
```

Архитектурная ошибка видна сразу при запуске, и искать её вручную в коде не придётся.

Подробнее о цепочках импортов, реэкспорте и подмене реализаций — в разделе [Инкапсуляция модулей](../fundamentals/encapsulation.md).

> `exports` управляет только внедрением зависимостей. Контроллеры, фоновые службы и инструменты модуля работают в любом случае. Доступ к API и другим точкам входа настраивается отдельно, например через `@Authorize`.

## Глобальные модули

Некоторые компоненты нужны почти везде: системные часы, логгер, подключения к инфраструктуре, кэш. Для них есть глобальные модули с декоратором `@Global()`:

```ts
import { Global, Module, singletonValue } from "bazis/core/di";

@Global()
@Module({
  providers: [singletonValue(CLOCK, systemClock)],
  exports: [CLOCK],
})
export class ClockModule {}
```

То, что глобальный модуль отдаёт через `exports`, доступно всем модулям без `imports`.

Глобальные модули хороши для инфраструктуры. Для бизнес-функциональности оставляйте явные `imports`: по ним видно, кто от кого зависит.

## Создание модулей через CLI

Модули создаются командой CLI. Не нужно вручную заводить файлы, подключать модуль к приложению и писать заготовки.

```bash
bunx bazis g module User --empty
```

CLI создаст пустой модуль с паспортом `MODULE.md` и подключит его к корневому модулю.

Выберите шаблон под задачу:

| Команда | Результат |
|---|---|
| `bunx bazis g module User --empty` | Пустой модуль с паспортом |
| `bunx bazis g module User` или `--minimal` | Готовая основа CRUD-модуля: модель, контекст БД, контракт и сервис, контроллер, модели запросов |
| `bunx bazis g module User --full` | CRUD-модуль плюс кэш, авторизация, фоновая служба и AI-инструмент |
| `bunx bazis g pack Catalog --parts items,categories` | Составной модуль из нескольких независимых частей |
| `bunx bazis g module Prices --pack Catalog` | Ещё одна часть в готовом составном модуле |

CLI подготовит структуру, а вы сосредоточитесь на бизнес-логике.

## Когда разделять функциональность на модули

Принцип простой: **одна функциональность — один модуль.** Пользователи, каталог, уведомления и отчёты — отдельные модули, у каждого своя ответственность.

Не создавайте отдельные модули для контроллеров, сервисов или моделей только потому, что это разные технические слои. Всё, что относится к одной функциональности, живёт в одном модуле.

Составной модуль нужен, когда внутри функциональности есть несколько самостоятельных частей со своими данными, логикой и ответственностью. Например, каталог:

- `ItemsModule` — товары;
- `CategoriesModule` — категории;
- `CatalogModule` — собирает обе части.

Составной модуль не добавляет слой бизнес-логики. Он только собирает части в более крупный блок.

Подробнее — в разделе [Архитектура модулей](../fundamentals/module-architecture.md).

## Структура модуля

CLI раскладывает модуль по папкам. Папка появляется, только когда в ней есть код, поэтому пустых каталогов нет.

```text
user/
├── MODULE.md                 паспорт модуля
├── User.module.ts            подключение модуля
├── model/                    модели и контекст БД
├── services/                 бизнес-логика и контракты сервисов
├── http/                     HTTP-контроллеры
│   └── contracts/            модели запросов и ответов
├── background/               фоновые службы
├── ai/                       AI-инструменты
└── test/                     тесты
```

`MODULE.md` — паспорт модуля: назначение, ответственность, входы и зависимости. По паспорту в проекте быстро разбирается и новый разработчик, и AI-ассистент. В новом проекте `AGENTS.md` прямо просит ассистента создавать модули через CLI и заполнять паспорт.

## Почему модули bazis

- **Всё в одном месте.** Функциональность целиком лежит в одной папке.
- **Явные зависимости.** Модуль сам говорит, от чего зависит и что отдаёт.
- **Границы под контролем.** bazis проверяет их при запуске и подсказывает, как исправить ошибку.
- **Рост без перестройки.** Новые возможности добавляются в модуль или новым модулем, остальное приложение не меняется.
- **Старт одной командой.** CLI создаёт структуру, подключение, паспорт и заготовки.
- **Единый подход.** HTTP, база данных, фоновые задачи, WebSocket, gRPC, бизнес-процессы, права и AI-инструменты — части одной функциональности.
